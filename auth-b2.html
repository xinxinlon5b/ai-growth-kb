一、定位

如果说 B1（Pete Hunt）讲的是 LLM 应用怎么生产化，
那 B2 讲的是 Agent 系统怎么架构设计——是 A2（生产级 Agent 白皮书）的工程化展开。

这本是 Agent 架构圣经。
客户问"你们的 Agent 跟竞品有什么不同"，答案在架构层面。

二、五大核心论点

1. Agent 编排范式（Orchestration Patterns）

不是所有 Agent 都一样，按编排方式分：

范式 特征 适合场景
单 Agent + 工具 一个大脑调 N 个工具 客服 / 简单问答
多 Agent 流水线 Agent1 → Agent2 → Agent3 文档处理 / 多步骤流程
多 Agent 协作 多个 Agent 互相调用 复杂决策 / 模拟场景
Agent + 人工 Agent 提议 + 人工确认 高风险业务

对应你 SOP-03 第 3 步"立刚性规则再谈 AI"——
风险越高的业务，越要选人机协作范式。

2. 状态管理（State Management）

Agent 是有状态的，状态管理是 Agent 系统最难的工程问题：

  • 会话状态：当前对话上下文
  • 任务状态：执行到哪一步了
  • 业务状态：操作数据库产生的真实数据
  • 记忆状态：长期记忆 / 用户偏好

反模式：把状态全塞进 Prompt → Token 爆炸 + 性能崩
正解：分层存储 + 摘要 + 外部记忆库

对应你 SOP-04「Agent 工具链」第 3 步"给 AI 立硬规则"——
状态要显式管理，不能靠 Prompt 隐性传递。

3. Tool / Skill 的封装、版本、复用

Tool 和 Skill 不是"调一个 API 那么简单"，要：

  • 封装：统一接口（输入输出 schema）
  • 版本：每个 Tool 有版本号，老调用不破坏
  • 复用：跨 Agent 共享 Tool 库
  • 测试：每个 Tool 独立可测
  • 监控：Tool 调用成功率、延迟、成本

对应你 SOP-04 第 5 步"沉淀成 Skill"——
Skill 不沉淀，Agent 就是一次性玩具。

4. Harness / Guardrail / 业务回滚（与 A2 呼应）

A2 讲了概念，B2 给了实现细节：

概念 实现方式
Harness 一个 Python/TS 类，包裹 Agent 调用
Guardrail 输入校验器 + 输出过滤器 + 动作拦截器
业务回滚 Saga 模式 / 补偿事务 / 软删除 + 反向操作

业务回滚 ≠ 模型回滚：
- 模型回滚：换回老模型版本
- 业务回滚：撤销 Agent 已经造成的业务影响（发出去的邮件撤回、创建的订单取消、转账退款）

对应你 SOP-03 第 4 步"留人工兜底验收"——
业务回滚是护栏的最后一道防线。

5. 高危动作拦截 + 人工接管

按动作风险分级处理：

动作 风险 处理
查订单 L0 Agent 自动
改备注 L1 Agent 自动 + 日志
发邮件 L2 Agent 提交 + 异步通知
退款 < 1000 元 L3 Agent 提交 + 人工确认
退款 > 1000 元 L4 必须人工执行

对应你 SOP-07「报价签约」交付标准——
风险分级要写进合同，不能口头约定。

十一、State Management 4 层架构

第 1 层：会话状态（Session State）

  • 存什么：当前对话上下文（最近 N 轮）
  • 存哪：Redis / 内存
  • TTL：对话结束 N 分钟后清

第 2 层：任务状态（Task State）

  • 存什么：当前任务进度（已做 / 待做 / 失败）
  • 存哪：PostgreSQL / SQLite
  • TTL：任务结束 N 天后归档

第 3 层：业务状态（Business State）

  • 存什么：Agent 操作产生的真实业务数据
  • 存哪：业务系统（订单表 / 用户表）
  • TTL：跟随业务规则

第 4 层：记忆状态（Memory State）

  • 存什么：用户长期偏好 / 历史交互
  • 存哪：向量数据库 / 长期存储
  • TTL：永久（用户可删）

十二、3 个反模式

反模式 1：把状态全塞进 Prompt

症状：把所有历史塞进 system prompt。
风险：Token 爆炸 + 性能崩 + 上下文窗口超限。
正解：分层存储 + 摘要压缩 + 按需加载。

反模式 2：状态不持久化

症状：Agent 重启后丢失所有上下文。
风险：用户体验断层 + 数据丢失。
正解：关键状态写数据库（不是只放内存）。

反模式 3：忽略状态同步

症状：Agent 改了业务数据，但业务系统没收到通知。
风险：数据不一致 + 业务流程断。
正解：事件驱动 + 消息队列 + 同步机制。

十一、原文核心（Adele Lin · Designing Agentic Systems · O'Reilly）

1. Agent 系统的 4 层架构（Adele Lin 框架）

层 职责 关键组件
第 1 层：Reasoning 思考 / 规划 LLM, CoT, ReAct
第 2 层：Memory 短期 + 长期 会话状态, 向量库
第 3 层：Tools 外部能力 API, RAG, 代码执行
第 4 层：Orchestration 协调 编排框架

2. Reasoning 层的 3 大技术

技术 1：Chain-of-Thought（CoT）

  • 思想：让 LLM 一步一步想
  • 实现：在 Prompt 中加 "Let's think step by step"
  • 效果：复杂推理任务准确率 +20-40%

技术 2：ReAct（Reasoning + Acting）

  • 思想：思考 + 行动 + 观察循环
  • 公式：Thought → Action → Observation → Thought → ...
  • 适合：需要工具调用的 Agent

技术 3：Plan-and-Execute

  • 思想：先做完整计划，再逐步执行
  • 适合：长期任务、多步流程
  • 代表：BabyAGI, AutoGPT

3. Memory 层的 4 种设计

类型 范围 例子
短期（会话） 当前对话 Redis / 内存
长期（用户） 用户偏好 PostgreSQL
长期（业务） 业务实体 业务系统表
长期（知识） 文档 / 知识库 向量数据库

4. Tools 层的 3 大类

类型 例子
信息获取 搜索 / RAG / API 查询
状态修改 写数据库 / 改文件 / 发邮件
计算执行 Python REPL / SQL 查询

5. Orchestration 层的 4 大模式

模式 适合
Sequential（顺序） 线性流程
Parallel（并行） 独立子任务
Hierarchical（层级） 协调者 + 工人
Loop（循环） 持续改进

6. 与企业 FDE 项目的对应

Adele 框架 FDE 实战

Memory 短期 + 长期记忆选型

7. 7 个反模式

  1. 裸调模型（无 Harness）—— 见 A2
  2. 状态塞 Prompt（Token 爆炸）—— 用 Memory 层
  3. 所有动作 AI 自动（高危）—— 用 Guardrail
  4. 不写评测（不知道好坏）—— 用 MEASURE 层
  5. 忽略错误（静默失败）—— 显式 raise
  6. 循环无界（Token 爆炸）—— 强制 max_steps
  7. 工具过大（执行慢）—— 拆小 + 链式

📖 完整深度论述

本卡对应 Adele Lin《Designing Agentic Systems》(O'Reilly)。原书需订阅，以下为基于公开内容与工程实践的系统性深度论述。

为什么 Agent 系统需要专门的架构设计

一个常见的误解是："Agent 就是把 LLM 包一层循环，让它能调工具。" 这个理解在 Demo 阶段够用，但一进入生产就崩。原因是 LLM 与传统软件有一个根本差异：LLM 的输出是非确定性的。传统软件同一个输入永远得到同一个输出，而 LLM 同一个 prompt 每次可能给出不同结果。这意味着所有围绕"确定性"构建的软件工程方法——精确的状态机、严格的事务、可复现的测试——在 Agent 系统里都需要重新设计。

因此，Agent 系统的架构设计，本质上是在回答一个问题：如何在一个非确定性核心（LLM）之上，构建一个确定性的、可预测的、可回滚的业务系统？ Adele Lin 的答案是把系统拆成四层——Reasoning、Memory、Tools、Orchestration——每一层都专门处理"非确定性"带来的某类风险。

Reasoning 层：把"思考"工程化

Reasoning 层的核心不是"选哪个模型"，而是如何让模型的思考过程可控、可观察、可改进。三个关键技术在解决不同的问题：

  • Chain-of-Thought（思维链）解决的是"模型跳步导致错误"的问题——通过强制模型一步步推理，把隐式的思考显式化，准确率能提升 20-40%。但它的代价是更多 token、更高延迟。
  • ReAct（推理+行动）解决的是"模型不知道何时该调工具"的问题——通过 Thought→Action→Observation 的循环，让模型在"想"和"做"之间交替。这是 Agent 区别于普通 LLM 调用的核心机制。
  • Plan-and-Execute（先规划后执行）解决的是"复杂任务需要全局观"的问题——先让模型做一个完整计划，再逐步执行，避免短视。

理解这三种技术的本质，你就能判断：不是所有任务都需要 ReAct 或 Plan-and-Execute。简单的问答任务，一次 CoT 就够；需要调工具的，用 ReAct；需要多步且有全局依赖的，才用 Plan-and-Execute。盲目堆叠只会增加成本和延迟。

Memory 层：状态是 Agent 系统的第一工程难题

Agent 系统的状态管理，比传统软件难一个数量级。传统软件的状态是显式的——变量、数据库、文件——程序员完全掌控。而 LLM 的"记忆"是隐式的——藏在 prompt 里、藏在上下文窗口里。

这带来一个致命的反模式：把状态全部塞进 prompt。开发者为了省事，把会话历史、用户偏好、业务上下文全塞进 system prompt，结果 token 爆炸、性能崩、上下文窗口超限。

正确的做法是分层存储：会话状态放内存（Redis）、任务状态放数据库（PostgreSQL）、业务状态放业务系统、长期记忆放向量库。每层有不同的生命周期、不同的访问模式、不同的持久化要求。只有把状态从 prompt 里"拎出来"，Agent 系统才能真正规模化。

Tools 层：工具的边界就是 Agent 的能力边界

一个常被忽视的事实：Agent 能做什么，完全取决于你给它什么工具，以及工具的文档写得多清楚。Anthropic 在构建 SWE-bench 智能体时发现，花在优化工具上的时间比整体 prompt 还多。

工具设计的关键是"站在模型的角度"。好的工具定义应该像给初级开发者写的优秀 docstring——包含示例用法、边界情况、输入格式要求、与其它工具的清晰边界。Poka-yoke（防呆）原则同样适用：改变参数让模型更难犯错。比如，模型用相对路径容易出错，就把工具改成强制要求绝对路径——从此模型完美使用。

Orchestration 层：简单优先，复杂度按需增加

编排层的四种模式——顺序、并行、层级、循环——对应四种复杂度需求。但核心原则是 Anthropic 反复强调的"简单优先"：从最简单的单 Agent 开始，只有当简单方案确实不够时，才增加编排复杂度。

这背后的逻辑是经济学的：每一次增加编排复杂度，都意味着更多的延迟、更多的成本、更多的失败点。如果单次 LLM 调用 + 检索就能解决问题，为什么还要上多 Agent 编排？只有当你明确测出"简单方案达不到目标"，复杂方案才值得。

一句话总结：Agent 架构设计的本质，是在非确定性 LLM 之上构建确定性业务系统——通过 Reasoning 控制思考、Memory 管理状态、Tools 界定能力、Orchestration 控制复杂度。
