B3 · 《RAG in Action》

类型：工程技术书 · RAG 工程实战
链接：Manning / 各大书店渠道
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

RAG（Retrieval-Augmented Generation，检索增强生成）是企业 AI 落地最常用的架构——
把企业私有知识库 + 大模型组合起来，让模型"看了再说"。

这本书是 RAG 工程化的"红宝书"。
你 KB 里"知识库项目 7 成是脏活"，那 7 成就是 RAG 数据准备。

二、五大核心论点

1. 什么时候需要 RAG，什么时候不需要

场景 RAG 原因
企业私有知识问答 ✓ 必须 模型不知道
实时信息查询 ✓ 推荐 模型知识过期
答案必须可追溯 ✓ 推荐 RAG 能引用原文
通用知识问答 ✗ 不需要 模型本身够
创意写作 ✗ 不建议 检索会干扰创作
强逻辑推理 ✗ 不需要 用 CoT / Tool Use

判断口诀：知识更新 + 来源可溯 → RAG；通用 + 创意 + 推理 → 不用 RAG。

2. RAG 召回效果验证方法

RAG 不是"丢进去就能用"，召回质量决定上限：

指标 释义 阈值建议
Recall@5 前 5 个结果里包含正确答案的比例 > 80%
MRR 正确答案的排名倒数 > 0.7
Context Precision 召回内容的精确度 > 0.8
Answer Faithfulness 答案忠实于原文（无幻觉） > 90%

测试方法：
- 准备 100-500 个真实问题 + 标准答案
- 跑 RAG 看召回对不对
- 看模型回答对不对 + 是否引用了原文
- 找最差的 20 个 case 改

对应你 SOP-03 第 4 步"持续迭代"——
RAG 不是一次做对，是每周调一次。

3. 幻觉测试方法

RAG 的最大风险是幻觉——模型"看似回答了你的问题，其实编的"。

三类幻觉：
- Context 没用上：召回对了但模型没看
- Context 不够：召回没召回完整信息
- Context 过度推断：模型基于召回做了过度推理

测试套路：
- 故意给错误文档 → 看模型会不会照搬
- 故意给空文档 → 看模型会不会说"不知道"
- 故意给部分文档 → 看模型会不会乱补全

对应 A3「企业 Agent 评估」的"边界验证"——
让模型在错误输入下不撒谎比答对重要。

4. 文档预处理与切分（Chunking）

RAG 的 7 成脏活在文档预处理：

  • 格式解析：PDF / Word / Excel / 图片 OCR
  • 结构保留：标题 / 章节 / 表格 / 列表
  • 切分策略：按段落 / 按 token / 按语义
  • 元数据：作者 / 时间 / 来源 / 标签
  • 去重 / 合并 / 过滤：垃圾文档先清掉

Chunking 黄金法则：
- 一段一段切，不要整篇丢
- 保留语义边界（不要把一句话切两半）
- 加 overlap（前后重复 10-20%）防截断
- 加 metadata（来源 / 时间 / 类型）

对应你方法论「知识库项目 7 成是脏活」——
脏活的 80% 在 chunking。

5. 召回策略与重排序（Rerank）

简单的"embedding 相似度召回"不够，需要多路召回 + 重排：

阶段 做法
召回 向量检索 + 关键词检索 + 元数据过滤（多路）
初排 相似度排序
重排 Cross-Encoder 模型精排（更准但更慢）
截断 取 Top-K 喂给 LLM

对应你的 SOP-04 第 5 步"沉淀成 Skill"——
RAG 配置（切分/召回/重排）应该作为 Skill 沉淀，下次复用。

三、关键术语（新增）

英文 中文 释义
RAG 检索增强生成 检索 + 生成的两段式架构
Chunking 文档切分 把长文档切成适合检索的小段
Recall@K Top-K 召回率 前 K 个结果里正确答案占比
MRR 平均倒数排名 正确答案排名的倒数
Faithfulness 忠实度 答案不偏离原文
Rerank 重排序 用更精确的模型二次排序
Embedding 向量化 把文本转成数字向量
