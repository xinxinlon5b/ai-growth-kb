06 · 避坑清单（13 个常见错误 · 实战版）

客户/自己常踩的坑 + 真相 + 出处 + 真实踩坑案例 + 救场步骤。

一、13 个常见错误

# 客户/自己常踩的坑 真相 出处 真实案例
1 客户花 30 万，3 个月没人用 没有真实+重复+有数据的业务前提 董俊豪 某客户想做"AI 客服"，3 个月后只有行政在用写周报。教训：先看历史数据是否污染，否则做不成。
2 按 Agent 数报价 卖工具不是做转型 制造业AI落地官 客户问"一个 Agent 多少钱"时——这是买工具思维。诊断+方案+落地才能报。
3 企业没数据就上 AI AI 前提是数据，先补数字化课 旭东14 制造业客户没 ERP、没知识库——AI 没有燃料。先帮他们数字化，再谈 AI。
4 跳过可行性就开工 半年后发现数据根本不够用 38号 FDE 教程 客户说"我有数据"——其实是几个孤立的 Excel。要先盘点真实性。
5 用脱敏样例数据做 POC 概念验证坟墓的第一块砖 范冰 FDE 书 POC 用脱敏样例 = 上线后真实数据全跑不通 = 客户投诉 = 重新做。
6 截止日期没写死 6 个月后变成大项目 范冰 FDE 书 每周一"再延一周"——6 个月后变什么都想要的大项目。教训：MVD 必须 1-5 天 / 4-8 周硬截止。
7 客户不让碰真实数据 = 高危信号 他不是来真的 旭东AI 客户说"先证明能力再给数据"——这是不愿意为项目负责的信号。教训：直接 Pass。
8 没画政治地图 上线演示被反噬 范冰 FDE 书 角落里另一部门主管一言不发——他要维护的流程正是你自动化掉的。教训：先识别受损者，给他们设计新出路。
9 评测集用 demo 数据 上线就翻车 38号 FDE 教程 评测集 50-100 条必须来自客户真实业务素材，不是工程师编的。
10 按"功能重要度"排迭代 部署期最该做的"上手使用"被延后 范冰 FDE 书 配色问题如果让用户觉得"这是给办公室白领做的"，它就是最高优先级——按使用阻塞度排，不是功能重要度。
11 来者不拒被合同额冲昏头 两个月后精英团队陷在低质量客户里 范冰 FDE 书 排期原则被销售压——最后崩的是交付质量。教训：宁可让销售把"档期排到下季度"当稀缺性卖。
12 把交付当纯成本 3 个客户都掉同一个坑，没人记录 范冰 FDE 书 沉淀当"研发账"上算——同样的坑，沉淀后第 4 个客户避免。
13 沉淀了就锁起来 团队各干各的，复利效应起不来 范冰 FDE 书 沉淀的 Skill 库 / 组件库 / 清单要团队共享——锁起来 = 浪费。

二、按项目阶段的避坑地图

阶段 0：立项选赛道（避坑 1-3）

  • ❌ 客户没真实+重复+有数据 → 拒绝接
  • ❌ 客户按 Agent 数报价 → 教育他"这不是工具"
  • ❌ 客户没数字化基础 → 转数字化小单

阶段 1-2：定义结果 + 调研（避坑 4-5）

  • ❌ 跳过可行性就开工 → 半年后悔
  • ❌ 用脱敏样例做 POC → 上线翻车

阶段 3：POC + 评测（避坑 6-7）

  • ❌ 截止日期没写死 → 6 个月坟墓
  • ❌ 客户不让碰真数据 → 高危信号

阶段 4：企业集成（避坑 8-9）

  • ❌ 没画政治地图 → 上线被反噬
  • ❌ 评测集用 demo 数据 → 翻车

阶段 5：上线 + 采用（避坑 10）

  • ❌ 按"功能重要度"排 → 部署期最该做的被延后

阶段 6-7：守约 + 复盘（避坑 11-13）

  • ❌ 来者不拒 → 团队崩
  • ❌ 不沉淀 = 永远从零开始
  • ❌ 沉淀了不共享 = 浪费

三、13 个救场步骤

每条坑都有具体救场话术 / 行动：

救坑 1：客户 30 万打水漂

症状：3 个月没人用。
救场：
1. 立刻出根因分析报告
2. 找到那块"真实+重复+有数据+可校验"的小业务
3. 重做 POC 跑通
4. 重新谈合同（按效果付费）

救坑 2：客户按 Agent 数报价

症状：客户问"一个 Agent 多少钱"。
救场：
1. 不直接回答
2. 问"您用这个 Agent 解决什么业务问题"
3. 引到"业务复杂度"和"价值评估"
4. 按"诊断+方案+落地"重新报价

救坑 3：企业没数据

症状：客户 IT 部门告诉你"我们没什么数据"。
救场：
1. 立刻盘点（用数据盘点清单）
2. 找出 Excel / 微信 / 邮件里的"非结构化数据"
3. 提议"先数字化（标准化）"作为第一期
4. 数字化的 3-6 个月后再谈 AI

救坑 4：可行性失败

症状：开工 3 个月发现数据根本不够。
救场：
1. 立即止损
2. 重新做 PSF 判断书
3. 评估是否还有"小块"业务可以做
4. 没有就 Pass 客户，转下一个

救坑 5：脱敏样例翻车

症状：POC 跑通但真实数据全错。
救场：
1. 立刻换真实数据重新 POC
2. 重新建评测集
3. 重新培训客户对 POC 的预期
4. 这次 POC 时间延长 1-2 周

救坑 6：截止日期模糊

症状：项目从 4 周拖到 12 周。
救场：
1. 重新写硬截止（不超过 2 周延）
2. 砍范围不缩价值（MVD 三军规）
3. 上线后立刻进入"增量扩展"而非"无限补全"

救坑 7：客户不让碰数据

症状：客户说"先证明能力再给数据"。
救场：
1. 直接 Pass 这个客户
2. 不值得为"非真客户"浪费时间
3. 用更典型的真实客户做案例

救坑 8：政治反噬

症状：上线演示被另一部门主管挑战。
救场：
1. 立即承认问题
2. 把这位主管纳入"支持者经营"
3. 给他设计"新角色"（如 AI 训练师）
4. 公开承诺不裁员，让他安心

救坑 9：评测集是 demo

症状：上线后 30% 错误率，评测时只有 5%。
救场：
1. 立刻回滚到上一个稳定版本
2. 重新建评测集（必须来自客户真实业务素材）
3. 重新训练 / 调 prompt
4. 复测通过后再上线

救坑 10：部署期上手慢

症状：上线 1 个月，使用率 < 30%。
救场：
1. 立即进入"热修复文化"
2. 反馈直达写代码的人
3. 每天收工问"今天的改动让用户明天的哪一刻更顺了"
4. 1-2 周内使用率应升到 60%+

救坑 11：接错灯塔

症状：接了"需求蝗虫"客户，2 个月后团队崩溃。
救场：
1. 立即终止合同
2. 按"客户优先级矩阵"重排剩余客户
3. 短期内拒绝销售线索
4. 重新校准"灯塔价值 + 学习价值"双维度

救坑 12：不沉淀

症状：第 3 个客户掉同一个坑。
救场：
1. 立即做"坑-解药"对照表
2. 沉淀到 Skill 库 / 组件库 / 检查清单
3. 培训团队共享
4. 下个客户用上

救坑 13：沉淀了不共享

症状：团队成员各自有沉淀但不通气。
救场：
1. 每周沉淀分享会（30 分钟）
2. 强制要求所有 Skill 进共享库
3. 月度最佳沉淀评选
4. 沉淀数纳入考核（不是质量，只是数）

四、3 个反模式

反模式 1：把避坑清单当 KPI

症状：用 13 个坑考核团队。
风险：团队为避坑而保守。
正解：避坑是参考，不是 KPI。

反模式 2：死守"不要重复踩坑"

症状：每个新场景都套避坑清单。
风险：创新被压制。
正解：避坑是"已知错误"+"容易犯"，新领域可以试错。

反模式 3：救场步骤不更新

症状：救场话术一直用旧的。
风险：新场景下失效。
正解：每季度复盘救场经验，更新清单。
