C3 · 领域驱动设计 DDD（Domain-Driven Design）

类型：通用软件建模方法论
作者：Eric Evans（2003 年出版，蓝皮书）
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

DDD 是企业软件建模的"圣经"——
讲的是怎么把客户的真实业务翻译成软件的代码结构。

FDE 进客户企业的第一步就是 DDD 思想的应用：
业务实体、领域规则、边界上下文——
这些是 DDD 的核心概念。

二、核心论点

1. 业务实体（Entity）和值对象（Value Object）

不是所有数据都同等重要，分两类：

类型 特征 例子
实体 有唯一 ID，状态可变 订单、客户、合同
值对象 无 ID，只描述属性 地址、金额、日期

实体的关键：能根据 ID 找到它，并追踪它的状态变化。
值对象的关键：值相同就是同一个，不关心是谁的。

对应你的 FDE「进厂先找数据」——
先识别核心实体，再围绕它们建数据流。

2. 聚合根（Aggregate Root）

实体之间有"父子关系"，聚合根是"父"：

订单（聚合根）
├── 订单项
├── 收货地址（值对象）
└── 支付记录

业务规则：要改订单项，必须通过订单这个根；不能直接改订单项。

对应 A2「生产级 Agent 白皮书」"动作边界"——
Agent 改数据必须按聚合根改，不能改一半留一半。

3. 限界上下文（Bounded Context）

同一个词在不同部门可能意思不同：

部门 "客户"含义
销售 联系人 + 跟进记录
财务 开票主体 + 信用
售后 设备 + 服务记录

限界上下文 = 每个部门有自己的"客户"模型，互不污染。

对应你的方法论「跨部门 AI 难推」——
每个部门有自己的数据语义，不能强求统一。

4. 领域服务（Domain Service）

有些业务逻辑不属于任何实体，是"跨实体的动作"：

  • 跨账户转账（涉及两个账户聚合）
  • 订单取消（涉及订单、库存、支付三个聚合）
  • 报表生成（涉及多个数据源）

这些放领域服务里，不放实体里。

对应你的 SOP-03 第 3 步"立刚性规则"——
跨实体的业务逻辑单独封装，独立测试。

5. 业务本体建模（VDNA / 业务图谱）

FDE 进客户后要画"业务地图"——这是 DDD 在 AI 时代的延伸：

[业务全景]
├── [销售域]
│   ├── 实体：客户 / 商机 / 合同
│   ├── 流程：线索 → 商机 → 成交
│   └── 痛点：手动录入 / 跟进遗忘
├── [生产域]
│   ├── 实体：工单 / 物料 / 设备
│   ├── 流程：接单 → 生产 → 出货
│   └── 痛点：进度不透明

对应你的方法论「跟 1 号位挖真痛点」——
VDNA = DDD 在企业 AI 场景的可视化版本。

三、关键术语（新增）

英文 中文 释义
DDD 领域驱动设计 Eric Evans 的建模方法论
Entity 实体 有 ID 的领域对象
Value Object 值对象 无 ID 的属性集合
Aggregate 聚合 一组相关实体的根
Aggregate Root 聚合根 聚合的入口实体
Bounded Context 限界上下文 业务边界，每个边界内有自己的模型
Domain Service 领域服务 跨实体的业务逻辑
Ubiquitous Language 统一语言 业务和技术用同一套词汇
VDNA 业务本体图谱 FDE 进客户画的全景图

"FDE 进你们企业的第一步不是写代码，是按 DDD 思想做业务建模——
识别核心实体、画限界上下文、找领域服务、形成业务地图。
这套做法参照 Eric Evans 的蓝皮书，确保我们做的不是工具，是贴合你们业务实际的东西。"
