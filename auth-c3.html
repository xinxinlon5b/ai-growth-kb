C3 · 领域驱动设计 DDD（Domain-Driven Design）

类型：通用软件建模方法论
作者：Eric Evans（2003 年出版，蓝皮书）
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

DDD 是企业软件建模的"圣经"——
讲的是怎么把客户的真实业务翻译成软件的代码结构。

FDE 进客户企业的第一步就是 DDD 思想的应用：
业务实体、领域规则、边界上下文——
这些是 DDD 的核心概念。

二、核心论点

1. 业务实体（Entity）和值对象（Value Object）

不是所有数据都同等重要，分两类：

类型 特征 例子
实体 有唯一 ID，状态可变 订单、客户、合同
值对象 无 ID，只描述属性 地址、金额、日期

实体的关键：能根据 ID 找到它，并追踪它的状态变化。
值对象的关键：值相同就是同一个，不关心是谁的。

对应你的 FDE「进厂先找数据」——
先识别核心实体，再围绕它们建数据流。

2. 聚合根（Aggregate Root）

实体之间有"父子关系"，聚合根是"父"：

订单（聚合根）
├── 订单项
├── 收货地址（值对象）
└── 支付记录

业务规则：要改订单项，必须通过订单这个根；不能直接改订单项。

对应 A2「生产级 Agent 白皮书」"动作边界"——
Agent 改数据必须按聚合根改，不能改一半留一半。

3. 限界上下文（Bounded Context）

同一个词在不同部门可能意思不同：

部门 "客户"含义
销售 联系人 + 跟进记录
财务 开票主体 + 信用
售后 设备 + 服务记录

限界上下文 = 每个部门有自己的"客户"模型，互不污染。

对应你的方法论「跨部门 AI 难推」——
每个部门有自己的数据语义，不能强求统一。

4. 领域服务（Domain Service）

有些业务逻辑不属于任何实体，是"跨实体的动作"：

  • 跨账户转账（涉及两个账户聚合）
  • 订单取消（涉及订单、库存、支付三个聚合）
  • 报表生成（涉及多个数据源）

这些放领域服务里，不放实体里。

对应你的 SOP-03 第 3 步"立刚性规则"——
跨实体的业务逻辑单独封装，独立测试。

5. 业务本体建模（VDNA / 业务图谱）

FDE 进客户后要画"业务地图"——这是 DDD 在 AI 时代的延伸：

[业务全景]
├── [销售域]
│   ├── 实体：客户 / 商机 / 合同
│   ├── 流程：线索 → 商机 → 成交
│   └── 痛点：手动录入 / 跟进遗忘
├── [生产域]
│   ├── 实体：工单 / 物料 / 设备
│   ├── 流程：接单 → 生产 → 出货
│   └── 痛点：进度不透明

对应你的方法论「跟 1 号位挖真痛点」——
VDNA = DDD 在企业 AI 场景的可视化版本。

英文 中文 释义

"FDE 进你们企业的第一步不是写代码，是按 DDD 思想做业务建模——
识别核心实体、画限界上下文、找领域服务、形成业务地图。

六、回查与延伸

  • 蓝皮书：《Domain-Driven Design: Tackling Complexity in the Heart of Software》Eric Evans，2003
  • 红宝书：《Implementing Domain-Driven Design》Vaughn Vernon，2013（更工程化）
  • FDE 场景特化：VDNA（Visual Domain & Network Analysis）是 FDE 圈里对 DDD 的可视化延伸

十一、VDNA（业务本体图谱）5 步绘制法

步骤 1：识别业务实体

  • 和 1 号位聊 2 小时
  • 问："哪些东西是你每天要管的？"
  • 产出：实体清单（订单 / 客户 / 商品 / 库存...）

步骤 2：识别实体关系

  • 问："实体之间怎么连？"
  • 画图：客户→下单→订单→包含→商品
  • 产出：关系图

步骤 3：识别聚合根

  • 问："要改 X 必须通过 Y 吗？"
  • 标出聚合根（订单 / 客户）
  • 产出：聚合根列表

步骤 4：识别限界上下文

  • 问："'客户'在不同部门含义一样吗？"
  • 销售部客户 = 联系人
  • 财务部客户 = 开票主体
  • 产出：限界上下文（每个部门一个）

步骤 5：识别领域服务

  • 问："跨实体的动作放哪？"
  • 转账（跨账户）/ 订单取消（跨订单 + 库存 + 支付）
  • 产出：领域服务列表

十二、4 个反模式

反模式 1：实体识别靠拍脑袋

症状：工程师关在屋里画实体图。
风险：和真实业务脱节。
正解：必须和 1 号位 / 业务方聊。

反模式 2：强求"客户"统一

症状：想做一个"全局客户"模型统一所有部门。
风险：每个部门的语义被扭曲。
正解：每个限界上下文有自己的客户模型。

反模式 3：聚合根切错

症状：把订单项当独立实体可改。
风险：数据不一致。
正解：所有改动必须通过聚合根（订单）。

反模式 4：领域服务变成万能函数

症状：领域服务包揽所有业务。
风险：实体变贫血（无业务逻辑）。
正解：核心业务逻辑放实体，跨实体才用领域服务。
