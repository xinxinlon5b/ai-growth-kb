A1 · Anthropic《Effective Harnesses for Long-Running Agents》—— 完整中文全文翻译

原文标题：Effective harnesses for long-running agents
作者：Justin Young（Anthropic）
发布：2025 年 11 月 26 日
原文链接：https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
翻译说明：以下为原文完整中文翻译，保留所有章节、JSON 案例、四种失败模式表格、致谢。未跳过任何实质内容。

引言

智能体在跨多个上下文窗口工作时仍然面临挑战。我们从人类工程师身上寻找灵感，为长效智能体创造更高效的 harness。

随着 AI 智能体能力越来越强，开发者越来越多地让它们承担需要跨越数小时甚至数天的复杂任务。然而，让智能体在多个上下文窗口间持续取得进展，仍然是一个未解决的问题。

长效智能体的核心挑战是：它们必须在离散的会话中工作，而每个新会话开始时，对之前发生的事情没有记忆。想象一个由轮班工程师组成的软件项目——每个新工程师到来时，对上一班发生的事一无所知。由于上下文窗口有限，而大多数复杂项目无法在单个窗口内完成，智能体需要一种方式来在编码会话之间架起桥梁。

我们开发了一个双管齐下的解决方案，使 Claude Agent SDK 能跨多个上下文窗口有效工作：

  • Initializer agent（初始化智能体）：在第一次运行时设置环境。
  • Coding agent（编码智能体）：被要求在每个会话中做增量进展，同时为下一个会话留下清晰的产物。

你可以在附带的 quickstart 中找到代码示例。

长效智能体的问题

Claude Agent SDK 是一个强大的通用 agent harness，擅长编码，以及其它需要模型使用工具收集上下文、规划和执行的任务。它具有上下文管理能力（如 compaction），使智能体能够工作而不会耗尽上下文窗口。理论上，给定这种设置，智能体应该可能继续无限期地做有用的工作。

然而，compaction 并不足够。 开箱即用，即使是最前沿的编码模型 Opus 4.5 在 Claude Agent SDK 上跨多个上下文窗口循环运行，如果只给它一个高层 prompt（如"克隆一个 claude.ai"），也无法构建出生产质量的 web 应用。

Claude 的失败表现为两种模式：

首先，智能体倾向于一次做太多事——本质上尝试 one-shot 整个应用。这常常导致模型在实现中途耗尽上下文，让下一个会话面对半成品且无文档的功能。智能体不得不猜测发生了什么，并花费大量时间让基础应用重新跑起来。即使有 compaction，这种情况仍会发生，因为 compaction 并不总是向下一个智能体传递完全清晰的指令。

第二种失败模式通常在项目后期出现。在一些功能已经构建后，后来的智能体实例会环顾四周、看到进展已经做出，就宣布任务完成。

这将问题分解为两部分。首先，我们需要设置一个初始环境，为给定 prompt 所需的所有功能奠定基础，这将使智能体能够逐步、逐功能地工作。其次，我们应该提示每个智能体朝着目标做增量进展，同时在会话结束时让环境保持干净状态。所谓"干净状态"是指适合合并到 main 分支的代码：没有重大 bug，代码有序且文档齐全，一般来说，开发人员可以轻松开始新功能而无需先清理无关的混乱。

在内部实验时，我们使用两部分解决方案解决了这些问题：
- Initializer agent：第一次智能体会话使用专门的 prompt，要求模型设置初始环境：一个 init.sh 脚本、一个 claude-progress.txt 文件（记录智能体已经做过的事情）、以及一个初始 git commit（显示添加了哪些文件）。
- Coding agent：每个后续会话要求模型做增量进展，然后留下结构化的更新。

这里的关键洞察是找到一种方式，让智能体在以全新上下文窗口开始时能快速理解工作状态——这是通过 claude-progress.txt 文件加上 git 历史实现的。这些做法的灵感来自了解有效的软件工程师每天在做什么。

环境管理

在更新的 Claude 4 prompting guide 中，我们分享了一些多上下文窗口工作流的最佳实践，包括一个 harness 结构，它对"第一个上下文窗口"使用不同的 prompt。这个"不同的 prompt"要求 initializer agent 设置环境，包含未来编码智能体有效工作所需的所有上下文。在这里，我们对这种环境的某些关键组件进行更深入的探讨。

功能列表（Feature List）

为了解决智能体 one-shot 整个应用或过早认为项目完成的问题，我们提示 initializer agent 写一份全面的功能需求文件，根据用户的初始 prompt 进行扩展。在 claude.ai 克隆的例子中，这意味着超过 200 个功能，例如"用户可以打开新聊天、输入查询、按回车、看到 AI 响应"。这些功能最初全部标记为"failing"，以便后来的编码智能体对完整功能应该是什么样子有清晰的概述：

{
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created",
    "Check that chat area shows welcome state",
    "Verify conversation appears in sidebar"
  ],
  "passes": false
}

我们提示编码智能体只能通过更改 passes 字段的状态来编辑此文件，并使用措辞强硬的指令，如"删除或编辑测试是不可接受的，因为这可能导致缺失或有 bug 的功能"。经过一些实验，我们最终确定使用 JSON，因为与 Markdown 文件相比，模型不太可能不当地更改或覆盖 JSON 文件。

增量进展（Incremental Progress）

有了初始环境脚手架后，下一版本的编码智能体被要求一次只做一个功能。这种增量方法对解决智能体一次做太多的倾向至关重要。

一旦增量工作，模型在改完代码后让环境保持干净状态仍然至关重要。在我们的实验中，我们发现让模型做这件事的最佳方式是要求模型使用描述性的 commit message 提交到 git，并在进度文件中写下进度摘要。这允许模型使用 git 回滚糟糕的代码更改并恢复代码库的工作状态。

这些方法也提高了效率，因为它们消除了智能体需要猜测发生了什么并花时间让基础应用重新工作的需要。

测试（Testing）

我们观察到的最后一个主要失败模式是 Claude 倾向于在没有适当测试的情况下标记功能完成。在缺乏显式提示的情况下，Claude 倾向于进行代码更改，甚至使用单元测试或对开发服务器的 curl 命令进行测试，但无法识别该功能并没有端到端工作。

在构建 web 应用的情况下，一旦明确提示 Claude 使用浏览器自动化工具、像人类用户一样进行所有测试，Claude 在端到端验证功能方面做得很好。Claude 通过 Puppeteer MCP 服务器在测试 claude.ai 克隆时拍摄的截图。

"Providing Claude with these kinds of testing tools dramatically improved performance, as the agent was able to identify and fix bugs that weren't obvious from the code alone."

为 Claude 提供这些类型的测试工具极大地提高了性能，因为智能体能够识别并修复从代码中看不出来的 bug。

仍然存在一些问题，比如 Claude 视觉和浏览器自动化工具的局限性，使其难以识别每种类型的 bug。例如，Claude 通过 Puppeteer MCP 看不到浏览器原生的 alert 弹窗，依赖这些弹窗的功能因此更容易出 bug。

快速进入状态（Getting up to speed）

有了上述所有设置，每个编码智能体都被提示运行一系列步骤来找到方向——有些是基本但仍然有用的：

  • 运行 pwd 查看你正在工作的目录。你只能编辑此目录中的文件。
  • 读取 git 日志和进度文件以了解最近的工作内容。
  • 读取功能列表文件并选择优先级最高且尚未完成的功能来处理。

"This approach saves Claude some tokens in every session since it doesn't have to figure out how to test the code. It also helps to ask the initializer agent to write an init.sh script that can run the development server, and then run through a basic end-to-end test before implementing a new feature."

这种方法在每个会话中为 Claude 节省一些 token，因为它不必弄清楚如何测试代码。它还有助于要求 initializer agent 写一个能运行开发服务器的 init.sh 脚本，然后在实现新功能之前运行一遍基础的端到端测试。

在 claude.ai 克隆的情况下，这意味着智能体总是启动本地开发服务器并使用 Puppeteer MCP 启动新聊天、发送消息并接收响应。这确保了 Claude 能够快速识别应用是否处于损坏状态，并立即修复任何现有的 bug。如果智能体反而开始实现新功能，它可能会使问题变得更糟。

鉴于此，一个典型的会话以下面的助手消息开始：

[Assistant] I'll start by getting my bearings and understanding the current state of the project.
[Tool Use] <bash - pwd>
[Tool Use] <read - claude-progress.txt>
[Tool Use] <read - feature_list.json>
[Assistant] Let me check the git log to see recent work.
[Tool Use] <bash - git log --oneline -20>
[Assistant] Now let me check if there's an init.sh script to restart the servers.
<Starts the development server>
[Assistant] Excellent! Now let me navigate to the application and verify that some fundamental features are still working.
<Tests basic functionality>
[Assistant] Based on my verification testing, I can see that the fundamental functionality is working well. The core chat features, theme switching, conversation loading, and error handling are all functioning correctly. Now let me review the tests.json file more comprehensively to understand what needs to be implemented next.
<Starts work on a new feature>

未来工作

这项研究展示了长效智能体 harness 中的一种可能方案，使模型能够跨多个上下文窗口做增量进展。然而，仍然存在未解决的问题。

最值得注意的是，是单一通用编码智能体在上下文中表现最好，还是通过多智能体架构可以实现更好的性能，仍然不清楚。专门的智能体（如测试智能体、质量保证智能体或代码清理智能体）可能在整个软件开发生命周期的子任务上做得更好似乎是合理的**。

此外，这个 demo 针对全栈 web 应用开发进行了优化。未来的方向是将这些发现推广到其他领域。这些经验中的一些或全部可能适用于其他类型的长效智能体任务，例如科学研究或金融建模。
