A1 · 《Forward Deployed Engineering》Anthropic 官方博客

类型：一手权威 · 厂商官方博客
发布：Anthropic，2024
链接：https://www.anthropic.com/blog/forward-deployed-engineering
中文卡版本：基于摘要整理 · 2026-09-10

一、源起与定位

Anthropic 把 FDE（前线部署工程师）从 Palantir 等传统数据公司的做法引入 AI 时代。
官方定义：FDE 工程师驻场到客户侧，把模型能力嵌入客户的真实业务系统，
对业务指标负责，现场迭代，并把经验反向沉淀回 Anthropic 平台。

这是 FDE 一词在 AI 行业最有权威的定义源头。
你的工作台里小智/旭东AI 等讲 FDE 的口播，都是这套官方叙事的二次传播。

二、核心论点（5 条）

1. 驻场 = 对业务结果负责，不是远程写代码

FDE 不是外包、不是咨询、不是售前。FDE 和客户团队坐在一起，
能看到真实业务数据、真实用户行为、真实失败模式。

这条直接对应你 SOP-03「FDE 入企交付」的第 1 步"进厂先找数据"。

2. POC 与生产投产是两回事

很多团队把 Demo 跑通当成项目完成——Anthropic 明确区分：
- POC：证明「这件事 AI 能做」
- 生产投产：证明「这件事 AI 在真实业务流里稳定、可靠、可回滚、可观测」

对应你 SOP-03 第 4 步"交付=Demo→落地→优化→培训"——很多 FDE 死在没走完后三步。

3. Harness（执行容器）是核心抽象

FDE 不是直接调模型，是给模型套一个 Harness——执行容器，负责：
- 工具调用管理
- 状态保存与恢复
- 动作边界（哪些动作允许、哪些必须人工确认）
- 错误隔离与回滚

这是「Agent + 护栏」一体的工程化形态。你 SOP-07「报价签约」里应该把这作为交付物。

4. Skill（技能包）是 FDE 的可复用资产

FDE 在客户现场沉淀的不是「代码」，是 Skill——把一次性的"我做了一遍"打包成
可复用的"下次直接调"。Anthropic 的 Skill 库是平台级资产，所有 FDE 共用。

对应你 SOP-04「Agent 工具链自用」第 5 步"沉淀成 Skill"——这是同一思路。

5. 业务护栏（Business Guardrail）来自真实失败

FDE 在客户现场见过的每一次"AI 做错了什么"都会沉淀成一条护栏。
护栏不是文档里的规范，是真实失败的反向工程。

对应你 SOP-03「FDE 入企 SOP」第 3 步"立刚性规则"。

三、关键术语（来自本文）

英文 中文 释义
Forward Deployed 前线部署 把工程师派到客户业务现场
Harness 执行容器 包裹模型的运行时，负责工具/状态/边界
Skill 技能包 一次工作流的可复用打包
POC 概念验证 证明"AI 能做"
Production 生产投产 证明"AI 在真实业务里稳跑"
Guardrail 护栏 防止 AI 出错的事前/事中约束

十一、3 个实战应用场景

场景 1：向客户解释"为什么需要 FDE"

场景：客户说"我们 IT 部门自己也能做 AI 项目"。

话术：

"FDE 不是一个开发岗位，是一个结果交付岗——
IT 部门做的是"项目上线"，FDE 做的是"客户业务改变"。

Anthropic 官方定义 FDE 是"对业务结果负责"——
不是代码写完，是客户团队工作方式真的变了。

这就是为什么 OpenAI 2025 年专门成立 The OpenAI Deployment Company
把 FDE 业务独立成公司——因为这不是开发问题，是落地问题。"

场景 2：向团队解释"为什么要做 Skill 沉淀"

场景：团队成员觉得"沉淀是浪费时间，做完下一个客户更重要"。

话术：

"Anthropic 的 FDE 团队把所有客户共性沉淀成 Skill 库——
平台级资产，所有 FDE 共用。

你不沉淀，第 11 个客户还要重新踩第 1 个客户的坑。
你沉淀了，第 1 个客户踩的坑救了第 11 个客户。

这是从「人海战术」到「复利团队」的关键差异。"

场景 3：向自己解释"什么时候该转产品化"

场景：你已经做了 5-10 个 FDE 项目，团队开始疲于奔命。

判断：
- 如果 3 个客户都掉同一个坑 → 不是客户的错，是你的方法没沉淀
- 如果客户需求 80% 重复 → 该把"项目制"转成"产品+配置"
- 如果销售可以独立接单 → 你已经从 FDE 升级到"产品公司"了

Anthropic 的路径：FDE → 沉淀 Skill → 平台产品 → 客户自服务。

十一、补充：Anthropic Harness 原始工程实现（2025 年 11 月原文）

来源：https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
这是 A1 的延伸阅读，因为 harness 是 FDE 交付的核心工程抽象

1. 长期 Agent 的核心问题

"The core challenge of long-running agents is that they must work in discrete sessions,
and each new session begins with no memory of what came before."

类比：工程师轮班，每个新工程师到来没有前班记忆。

两个失败模式：
1. 试图一次做完所有事 —— 中途 context 用完，下一班看到未完成功能得猜
2. 过早宣布完成 —— 看到有些功能已实现就 declare done

2. Anthropic 的解法：Initializer + Coding Agent

Initializer Agent（首次会话）

  • 目的：搭建后续工作环境
  • 产出：
  • init.sh 脚本
  • claude-progress.txt 进度日志
  • 初始 git commit（显示添加了哪些文件）
  • feature_list.json —— 完整功能列表

Coding Agent（后续每次会话）

  • 目的：做单次增量进展
  • 要求：
  • 只改一个 feature
  • 离开前 git commit 描述性 message
  • 在 progress 文件写结构化更新

3. Feature List 设计（关键！）

"To address the agent one-shotting an app,
we prompted the initializer agent to write a comprehensive file
of feature requirements expanding on the user's initial prompt.
In the claude.ai clone example, this meant over 200 features."

feature_list.json 结构（每条功能）：

{
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created",
    "Check that chat area shows welcome state",
    "Verify conversation appears in sidebar"
  ],
  "passes": false
}

关键规则：
- 全部初始标记为 passes: false
- 只能用 JSON（模型对 JSON 的编辑比 Markdown 谨慎）
- 强警告："删除或编辑测试是不可接受的"

4. 启动序列（每个新会话）

1. Run `pwd` 确认工作目录
2. Read git log + progress files 了解最近工作
3. Read feature list 选优先级最高且未完成的功能
4. 启动开发服务器（init.sh）
5. 用 Puppeteer MCP 做端到端测试
   - 新建聊天 / 发消息 / 收到回复
6. 如果有 bug → 立即修（不要先做新 feature）
7. 做新 feature
8. git commit 描述性 message
9. 更新 progress.txt

5. 端到端测试（关键差异）

"Claude tended to make code changes, and even do testing with unit tests or curl commands,
but would fail to recognize that the feature didn't work end-to-end."

改进：用 Puppeteer MCP 让 Claude 像人一样用浏览器测试。

"Providing Claude with these kinds of testing tools dramatically improved performance,
as the agent was able to identify and fix bugs that weren't obvious from the code alone."

6. 与企业 FDE 项目的映射

Anthropic Harness FDE 项目等效
claude-progress.txt 客户档案 + 交付日志
feature_list.json PSF 判断书 + 5 步报价法
Initializer Agent 入企尽调 5 张地图
Coding Agent MVD 4 周 Demo
Puppeteer MCP 测试 客户业务方人工验收
Git commit message 每单交付的复盘文档
Progress.txt 更新 每周项目状态同步

7. FDE 可以直接用的 5 个 harness 模式

  1. Initializer + 多 Coding Agent —— 1 周尽调 + 多周交付
  2. Feature List 拆任务 —— 把 1 个项目拆 50-200 个 feature
  3. 端到端测试 —— 让 FDE 真正用系统而不是看代码
  4. Git-style 进度文件 —— 客户能查的实时进度
  5. 结构化交接 —— FDE 离开前留下完整文档

8. 与 A1 主题的关联

A1 介绍 FDE 这个角色（人）。
本文介绍 FDE 工作用的工具（harness）。
两者共同构成 FDE 体系：
- 人：驻场 / 对业务结果负责 / 现场迭代
- 工具：harness 化思维 / 状态显式 / 增量进展

原文：Effective Harnesses for Long-Running Agents（长效智能体的高效 Harness）
作者：Justin Young（Anthropic）
发布：2025-11-26
原文链接：https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

引言

智能体在跨越多个上下文窗口工作时仍面临挑战。我们从人类工程师身上寻找灵感，为长效智能体创造更高效的 harness。

随着 AI 智能体能力越来越强，开发者越来越多地让它们承担需要跨越数小时甚至数天的复杂任务。然而，让智能体在多个上下文窗口间持续取得进展，仍然是一个未解决的问题。

长效智能体的核心挑战是：它们必须在离散的会话中工作，而每个新会话开始时对之前发生的事情没有记忆。

想象一个由轮班工程师组成的软件项目，每个新工程师到来时对上一班发生的事一无所知。因为上下文窗口有限，而大多数复杂项目无法在单个窗口内完成，智能体需要一种方式在编码会话之间架起桥梁。

我们开发了双管齐下的解决方案，让 Claude Agent SDK 能跨多个上下文窗口有效工作：
1. Initializer agent（初始化智能体）：在第一次运行时设置环境。
2. Coding agent（编码智能体）：在每个会话中做增量进展，同时为下一个会话留下清晰的产物。

长效智能体的问题

Claude Agent SDK 是一个强大的通用 agent harness，擅长编码，以及其它需要模型用工具收集上下文、规划和执行的任务。它有 compaction（压缩）等上下文管理能力，能让智能体在不耗尽上下文窗口的情况下工作。理论上，这种设置下智能体应该能无限期地持续做有用工作。

然而，compaction 并不够。 开箱即用，即使是最前沿的编码模型 Opus 4.5 在 Claude Agent SDK 上跨多个上下文窗口循环运行，如果只给它一个高层 prompt（如"克隆一个 claude.ai"），也无法构建出生产质量的 web 应用。

Claude 的失败表现为两种模式：

失败模式 1：试图一次做完所有事。 智能体倾向于"one-shot"整个应用。这常常导致模型在实现中途耗尽上下文，让下一个会话面对一个半成品且无文档的功能。智能体不得不猜测发生了什么，花大量时间让基础应用重新跑起来。即使有 compaction，这种情况仍会发生——因为 compaction 并不总能给下一个 agent 传递完全清晰的指令。

失败模式 2：过早宣布完成。 在项目后期，一些功能已经构建后，后来的 agent 实例会环顾四周、看到进展已经做了，就宣布任务完成。

这把问题分解成两部分：
1. 设置一个初始环境，为给定 prompt 所需的所有功能奠定基础——让智能体一步步、一个功能一个功能地工作。
2. 提示每个智能体朝着目标做增量进展，同时在会话结束时让环境保持干净状态。"干净状态"指的是适合合并到 main 分支的代码：没有重大 bug、代码有序且文档齐全、开发者能轻松开始新功能而无需先清理无关混乱。

环境管理

Feature List（功能列表）

为解决智能体 one-shot 应用或过早认为项目完成的问题，我们提示 initializer agent 写一份基于用户初始 prompt 扩展的完整功能需求文件。在 claude.ai 克隆的例子中，这意味着 200 多个功能，例如"用户可以打开新聊天、输入查询、按回车、看到 AI 响应"。

这些功能全部初始标记为 "failing"（失败），这样后续的 coding agent 就有了完整功能应该是什么样子的清晰大纲：

{
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created",
    "Check that chat area shows welcome state",
    "Verify conversation appears in sidebar"
  ],
  "passes": false
}

我们提示 coding agent 只能通过修改 passes 字段来编辑这个文件，并使用强硬措辞如"删除或编辑测试是不可接受的，因为这会导致缺失或有 bug 的功能"。经过一些实验，我们最终选择用 JSON——因为模型对 JSON 文件的不当修改或覆盖可能性低于 Markdown 文件。

Incremental Progress（增量进展）

有了初始环境脚手架，coding agent 的下一次迭代被要求一次只做一个功能。这种增量方法对解决智能体"一次做太多"的倾向至关重要。

做增量进展后，模型在改完代码后让环境保持干净状态仍然至关重要。实验发现，最好的方式是要求模型用描述性 commit message 提交到 git，并在进度文件中写进度摘要。这让模型能用 git 回滚坏代码改动、恢复代码库的工作状态。

这些方法也提升了效率——消除了 agent 猜测发生了什么、花时间让基础应用重新跑起来的需求。

Testing（测试）

我们观察到的最后一个主要失败模式是：Claude 倾向于在没有适当测试的情况下标记功能完成。缺乏显式提示时，Claude 倾向于改代码、甚至用单元测试或 curl 命令对开发服务器做测试，但无法识别功能并没有端到端工作。

在构建 web 应用时，一旦显式提示 Claude 使用浏览器自动化工具、像人类用户一样做所有测试，它在端到端验证功能上表现很好。

给 Claude 提供这类测试工具极大提升了性能，因为智能体能识别并修复仅从代码看不出来的 bug。

仍有一些问题，比如 Claude 视觉和浏览器自动化工具的局限，让它难以识别每一种 bug。例如，Claude 通过 Puppeteer MCP 看不到浏览器原生的 alert 弹窗，依赖这些弹窗的功能因此更容易出 bug。

Getting up to speed（快速进入状态）

有了以上所有设置，每个 coding agent 都被提示跑一系列步骤来"找到方向"：
- 运行 pwd 看工作目录（你只能编辑这个目录里的文件）；
- 读 git 日志和进度文件了解最近在做什么；
- 读功能列表文件，选择优先级最高且还没做的功能来做。

这让 Claude 每个会话省一些 token（不用再费劲想怎么测试代码）。同时，让 initializer agent 写一个能运行开发服务器的 init.sh 脚本，并在实现新功能前跑一遍基础端到端测试，也很有帮助。

一个典型会话的开场 assistant 消息序列：

[Assistant] 我先找到方向、了解项目当前状态。
[Tool Use] <bash - pwd>
[Tool Use] <read - claude-progress.txt>
[Tool Use] <read - feature_list.json>
[Assistant] 让我看 git log 了解最近的工作。
[Tool Use] <bash - git log --oneline -20>
[Assistant] 现在检查是否有 init.sh 脚本重启服务器。
<启动开发服务器>
[Assistant] 好，现在导航到应用，验证一些基础功能是否正常。
<测试基础功能>
[Assistant] 验证显示基础功能工作正常……现在看 tests.json，理解接下来要实现什么。
<开始做新功能>

四种失败模式与解决方案（总结表）

失败模式 Initializer Agent 行为 Coding Agent 行为
Claude 过早宣布整个项目完成 基于输入规格建立 feature list 文件（结构化 JSON 的端到端功能描述列表） 会话开始读 feature list，选择单个功能来做
Claude 让环境处于有 bug 或未文档化状态 写初始 git repo + 进度笔记文件 会话开始读进度文件和 git 提交日志，跑基础测试抓未文档化的 bug；会话结束写 git commit + 进度更新
Claude 过早标记功能完成 建立 feature list 文件 自验证所有功能，只在仔细测试后才标 "passing"
