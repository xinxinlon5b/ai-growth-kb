1.1 Anthropic FDE 博客《Forward Deployed Engineering》（2024）

原文出处：anthropic.com/blog/forward-deployed-engineering

一句话定义

FDE = 驻场客户的 AI 工程师，对业务指标负责，把模型能力嵌入真实业务系统，现场迭代，能力反向沉淀回平台。FDE 不交付 demo，交付可投产系统。

三大核心立场

  1. 业务指标优先（Business-outcome ownership）：FDE 不用模型 benchmark 验收，用业务 KPI（转化率、客诉率、AHT、人工替代率）验收。
  2. 驻场共创（Forward-deployed）：工程师去客户现场，与客户工程师结对写代码，而非远程"顾问咨询"。
  3. 平台-产品反哺（Platform feedback loop）：现场踩到的坑要抽象回平台/Harness/Skill/护栏，让下一位 FDE 不再踩。

POC vs 生产（Prototype vs Production）

Anthropic 明确区分两个阶段，FDE 主要工作在生产阶段：

维度 POC（原型） 生产（Production）
目标 证明可行性 保证 SLA、ROI、合规
评估 一次性 demo 持续指标 + 灰度 + 回滚
责任 工程师个人 FDE + SRE + 合规 + 客户团队
失败容忍 高 极低（需护栏、Harness）

关键判断：用户痛点里"看不出真伪"——解药就是生产级护栏 + 评估流水线，而不是再做一个 demo。

Harness / Skill / 护栏的来源

Anthropic 公开承认：Harness、Skill 库、业务护栏全部源于 FDE 实战沉淀，不是平台 PM 凭空设计。
这与本轮 SOP 中"FDE 现场沉淀"的设计哲学完全一致。

FDE 的六项关键工作

  1. 业务抽象（Business abstraction）：把客户业务翻译为可建模的 Agent 任务。
  2. 数据流重构（Data plumbing）：打通客户已有系统（CRM、ERP、工单）→ Agent。
  3. Harness 设计（Harness design）：为客户 LLM 调用装上工具调用、护栏、状态机。
  4. Skill 开发（Skill authorship）：把高频工具/提示封装为可复用 Skill。
  5. 评估流水线（Evals）：建立离线 + 在线指标，让效果可证伪。
  6. 上线护航（Production escort）：灰度、值班、应急响应。

FDE 反模式（Anthropic 警示）

  • ❌ 把"提示词跑通"当成"系统上线"。
  • ❌ 在客户环境里堆新组件。
  • ❌ 不沉淀到平台，每个项目从零开始。
  • ❌ 业务成果与模型效果混为一谈。

1.2 Anthropic《Building agents for production》白皮书

核心论点：Agent ≠ Chatbot。Agent 必须有 Harness（执行容器）+ Guardrail（动作护栏）+ 状态管理 + 故障隔离 + 业务动作回滚 才能投产。

Harness（执行容器）

  • 定义：包裹 Agent 行为的运行时：工具调用、循环、状态、超时、错误处理、权限沙箱。
  • 三要素：
    1. 执行循环（Execution loop）：ReAct / Plan-and-Execute 的循环结构。
    2. 状态管理（State）：短期记忆 + 长期记忆 + 工具历史。
    3. 终止条件（Termination）：最大步数、超时、人工介入、目标达成。

动作护栏（Action Guardrails）

  • 风险分级：读动作（低）→ 写动作（中）→ 外部副作用动作（高）。
  • 拦截策略：白名单、参数校验、人工审批（Human-in-the-loop）、回滚机制。
  • Anthropic 强约束：任何"不可逆动作"必须挂人工审批或预演。

状态管理（State Management）

  • 短期：上下文窗口（token）。
  • 中期：会话级持久化（Redis、Postgres）。
  • 长期：知识库 / 向量库 / 业务对象。

故障隔离（Fault Isolation）

  • 单个工具失败不能让整个 Agent 崩溃。
  • 每个工具有独立超时、重试、回滚边界。
  • 推荐 熔断器模式（Bulkhead / Circuit Breaker）。

业务动作回滚（Business Action Rollback）

这是 Anthropic 的核心创新点：模型回滚 ≠ 业务回滚。
- 模型回滚：换 checkpoint。
- 业务回滚：取消已发出的邮件、撤回审批、补偿订单、对冲支付。

FDE 的责任：在护栏里写"业务补偿函数"，而不是只盯着模型准确率。

人工接管（Human-in-the-Loop, HITL）

  • 高风险动作必须 HITL。
  • HITL 设计原则：单次确认、批量审批、超时默认策略、审计可追溯。

1.3 Anthropic《Evaluating AI agents in real enterprise workflows》

评估三件套

  1. 离线评估（Offline evals）：用历史数据 / 黄金集跑 Agent，得到可重复指标。
  2. 在线评估（Online evals）：线上真实流量的影子评估、A/B、人评抽样。
  3. 故障注入测试（Fault injection）：主动制造工具超时、错误响应、越权请求，验证护栏是否生效。

指标定义（KPI 设计）

Anthropic 推荐 4 类指标组合：

类别 示例
业务结果 转化率、AHT、人工替代率、CSAT
任务完成 任务成功率、平均步数、人工接管率
风险合规 越权率、违规率、PII 泄漏率
系统性能 P99 延迟、Token 单价、护栏误判率

边界验证（Boundary verification）

"可证伪"是 Anthropic 的核心哲学：每条护栏都要有对应的反向用例，证明它能在坏情况下拦住。

1.4 Pete Hunt《Building LLM Applications for Production》

作者：Hugging Face 核心工程师。这是企业 LLM 落地的"决策字典"——什么场景用什么组件。

RAG 决策矩阵（何时上 RAG，何时不上）

场景 决策
知识频繁变化（法规、产品手册） ✅ 上 RAG
私有知识 / 长尾文档 ✅ 上 RAG
通用知识 / 推理 / 创作 ❌ 不上 RAG（用原生模型 + 提示工程）
延迟极敏感（<200ms） ❌ 不上 RAG（推理成本高）
数据极少变化 ⚠️ 直接塞提示词更划算

模型网关（Model Gateway / Middle Layer）

Pete Hunt 强调：模型调用必须经过网关层，类似 API Gateway：

网关能力 作用
路由 多模型路由（OpenAI / Anthropic / 本地）
限流 防止成本失控 / 滥用
鉴权 API Key、RBAC、租户隔离
缓存 同语义 prompt 缓存、KV Cache
降级 模型超时自动降级到便宜模型
审计 全量日志、Token 消耗、Trace
A/B 多版本流量分配

这与本轮词典 [B 卷 · Middle 网关] 完全吻合。

风险分级（Risk Tiering）

Pete Hunt 把 LLM 应用分 3 级：

  • Tier 1（低风险）：内部 demo、内容生成、辅助写作 → 简单护栏。
  • Tier 2（中风险）：客服问答、知识检索 → RAG + 内容护栏。
  • Tier 3（高风险）：金融、医疗、法律、自动决策 → 全套护栏 + HITL + 审计 + 合规。

灰度 / 版本 / 回滚

  • 灰度：1% → 5% → 25% → 100%，每档观察 ≥ 30 分钟。
  • 版本管理：Prompt 版本、模型版本、Skill 版本独立管理。
  • 回滚：1 键回滚到任意历史快照（不是只回 checkpoint）。

可观测 / Trace / 日志

  • Trace ID：每次 LLM 调用打 Trace ID，串联所有工具调用。
  • 日志：输入、输出、Token 数、延迟、模型版本、护栏触发。
  • LangSmith / Langfuse / Helicone / Phoenix 任选其一。

1.5 Adele Lin《Designing Agentic Systems》（O'Reilly）

业界称为 Agent 架构圣经，对应 FDE 里 Agent + Skill + Harness 全栈。

Agent 编排范式

  • ReAct：边推理边行动。
  • Plan-and-Execute：先完整规划再执行。
  • Reflexion：行动后反思，更新记忆再行动。
  • Multi-Agent 协作：监督者、对等、层级、网络四种模式。

状态管理深度设计

  • 短期状态：对话上下文（token 限制）。
  • 会话状态：当前任务进度、变量。
  • 跨会话状态：用户偏好、历史任务。
  • 企业级状态：业务实体（订单、工单、合同）。

Tool / Skill 封装三原则

  1. 原子性：一个 Tool 做一件事。
  2. 可描述：Tool 必须有清晰的 Schema（输入、输出、错误）。
  3. 可版本化：Tool 升级不破坏旧调用。

约束框架 Harness 设计

  • 角色定义：Agent 的人设、能力边界。
  • 禁止动作清单：明确不能做的（写库、发邮件、改权限）。
  • 必须确认动作：高风险动作必须 HITL。
  • 资源限制：最大步数、最大 Token、最大工具调用数。

动作风险分级（Action Risk Tiering）

Adele Lin 把 Agent 动作分 5 级：

级别 示例 护栏
L0 只读 查文档、查订单 无需审批
L1 内部写 写缓存、写日志 速率限制
L2 业务写 改订单、改工单 HITL
L3 外部副作用 发邮件、发短信 HITL + 内容护栏 + 回执
L4 不可逆 转账、删数据、撤稿 强制双签 + 异步队列 + 补偿函数

业务层回滚（Business Rollback）

这是 Adele Lin 与 Anthropic 共同的强调点：回滚是业务动作，不是模型动作。

模型回滚（无效） 业务回滚（有效）
换一个 checkpoint 撤回已发的邮件
重新生成答案 撤销订单
调整 prompt 补偿支付
对冲扣款

1.6 《RAG in Action》核心提炼

RAG 决策四问

  1. 知识是否频繁变化？ → 是则 RAG，否则提示词够用。
  2. 是否私有/长尾？ → 是则 RAG。
  3. 是否可接受 1-3s 延迟？ → 否则考虑 KV Cache / 预生成。
  4. 评估指标是否达标？ → 不达标要调 Chunk / Embedding / Rerank。

召回效果验证三件套

  • 召回率（Recall@k）：相关文档被召回了多少。
  • 精确率（Precision@k）：召回结果里有多少相关。
  • MRR / NDCG：排名质量。

幻觉测试方法

  • 无答案检测：检索为空时模型应拒绝回答，而非编造。
  • 答案可追溯：每条结论必须能溯源到文档。
  • Faithfulness 评分：RAGAS 的核心指标。

1.7 《LLM Security and Governance》核心提炼

内容安全 3 层

  1. 输入侧：Prompt 注入检测、越狱识别、恶意输入过滤。
  2. 输出侧：PII 过滤、违规内容拦截、敏感词审查。
  3. 过程侧：审计日志、Trace、可解释性。

权限模型

  • RBAC：按角色授权 Agent 可调用哪些 Tool。
  • ABAC：按属性（部门、租户、敏感级）授权。
  • 最小特权：Agent 默认无任何特权，按需临时申请。

审计与合规

  • 全量日志：每次 LLM 调用、每次 Tool 调用、每次 HITL 审批。
  • 不可篡改：审计日志写入只读存储（WORM）。
  • 可回溯：任意时刻可还原完整决策链路。

风险边界

场景 风险等级 必要护栏
内部知识问答 中 内容审核 + 审计
客服自动回复 中高 风险分级 + HITL
自动决策 高 双签 + 强制 HITL
金融/医疗 极高 监管合规 + 人工最终决策

2.1 风险驱动架构（Risk-Driven Architecture）

方法论来源：《Software Architecture: Foundations, Theory, and Practice》

核心思想

架构组件不是越多越好，架构决策由风险驱动。 只有识别到对应风险，才引入对应防护组件；没有风险，就不增加组件，避免过度工程。

FDE 决策矩阵（本轮核心交付）

业务风险 引入组件 不引入的后果
写数据 / 不可逆操作 Harness + 业务回滚 + HITL 误操作无法撤销
多模型切换 Middle 网关（路由 + 限流 + 缓存） 切换成本失控
幻觉 / 不实回答 RAG + 内容护栏 + Faithfulness 评估 用户被误导
PII / 数据泄漏 PII 过滤 + 审计日志 + RBAC 合规事故
高并发 / 成本失控 限流 + 缓存 + 降级 账单爆炸
越权 / Prompt 注入 输入护栏 + 工具白名单 安全事故
响应延迟不稳 SLO + 熔断 + 灰度 用户体验差
业务漂移 / 知识过期 RAG + 在线评估 + 周期性回测 系统失能
Agent 失控循环 最大步数 + 超时 + 终止条件 资源耗尽
跨租户泄漏 多租户隔离 + 命名空间 + 网关 数据事故

关键原则

  • YAGNI（You Aren't Gonna Need It）：风险未出现，不预先构建。
  • 从简到繁：先最小可行 → 出现风险 → 加防护。
  • 可逆性优先：选择可逆决策（提示词 vs 微调）；不可逆决策（基础设施、合同）慎之又慎。

2.2 混沌工程（Chaos Engineering）

书籍：《Chaos Engineering: Resilience through Controlled Disruption》（Netflix 等）

四大原则（Principles of Chaos）

  1. 建立稳态假设：先定义正常行为的样子。
  2. 多样化真实世界事件：模拟真实故障而非凭空制造。
  3. 在生产环境运行：测试环境无法替代生产环境的复杂性。
  4. 自动化持续演练：把故障演练嵌入 CI/CD。

FDE 投产前的故障注入清单

故障类型 注入工具 验证目标
工具超时 Toxiproxy、Chaos Mesh Harness 超时熔断
工具错误响应 自定义 hook Agent 不崩溃、优雅降级
LLM API 限流 网关层模拟 降级路由生效
数据库故障 自定义 业务回滚启动
网络分区 Chaos Mesh 缓存兜底
Prompt 注入 红队用例 输入护栏生效
越权请求 RBAC 测试 拒绝执行
资源耗尽 压测 最大步数生效

Netflix 三大传统武器

  • Chaos Monkey：随机杀实例。
  • Chaos Gorilla：模拟整个可用区故障。
  • Chaos Kong：模拟整个区域故障。

FDE 投产护航清单（Chaos-Inspired）

  • ✅ 工具超时已演练
  • ✅ 模型降级已演练
  • ✅ Prompt 注入已演练
  • ✅ 业务回滚已演练
  • ✅ 跨租户隔离已演练
  • ✅ HITL 切换已演练
  • ✅ 审计日志已演练

2.3 领域驱动设计（Domain-Driven Design）

书籍：《Domain-Driven Design》Eric Evans

核心概念（对应 FDE 进场第一步）

概念 含义 FDE 应用
实体（Entity） 有唯一标识的对象 客户、订单、工单
值对象（Value Object） 无标识的描述性对象 地址、金额
聚合根（Aggregate Root） 一致性边界 订单聚合根管理订单项
限界上下文（Bounded Context） 模型的适用边界 销售域 / 售后域 / 财务域
领域事件（Domain Event） 业务发生的事 订单已下单、支付已完成
领域服务（Domain Service） 不属于实体的业务逻辑 转账服务、定价服务
仓储（Repository） 持久化抽象 订单仓储
工厂（Factory） 复杂对象创建 订单工厂

VDNA 模型（Value-Domain-Notion-Action）

FDE 进场标准动作：

  1. Value（价值）：这个业务的价值流是什么？客户为什么买单？
  2. Domain（领域）：核心领域是什么？哪些是关键实体？
  3. Notion（概念）：领域专家用哪些术语？这些术语的中文/英文映射是什么？
  4. Action（动作）：日常发生哪些动作？谁来做？

战略设计 vs 战术设计

  • 战略设计：限界上下文、上下文映射、领域划分。
  • 战术设计：实体、值对象、聚合、领域事件、领域服务。

FDE 进场先战略后战术，避免一上来就建表。

通用语言（Ubiquitous Language）

  • FDE 必须学会客户的"行话"。
  • 文档、代码、对话必须用同一套术语。
  • 这与词典项目的"专业大词典"完全契合。

3.1 Google Agent Design Framework（公开版要点）

四大核心原则

  1. 风险分级：每个工具调用都标记风险等级。
  2. 动作白名单：Agent 只能做白名单里的事。
  3. 人机交接：高风险动作必须 HITL。
  4. 持续评估：离线 + 在线 + 故障注入三件套。

3.3 OpenAI Agent Best Practices

五大最佳实践

  1. Tool 风险分级：每个 Tool 必须标风险等级。
  2. 评估流水线：Evals API + 自定义指标。
  3. HITL 设计：高风险 Tool 强制人工审批。
  4. 错误处理：工具失败降级、重试、退回人类。
  5. 审计：全量日志 + Trace + 可视化。

OpenAI 与 Anthropic 的互补

  • OpenAI：API + 函数调用 + 评估 API。
  • Anthropic：FDE 实践 + Harness 哲学 + 业务回滚。
