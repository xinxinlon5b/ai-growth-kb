A3 · 《Evaluating AI agents in real enterprise workflows》企业 Agent 评估方法论

类型：一手权威 · 评估方法论
发布：Anthropic
链接：anthropic.com（评估专题）
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

A1 讲 FDE 是什么，A2 讲 Agent 怎么造，A3 讲 Agent 怎么证明自己能用。

这是「怎么证明 AI 真的把客户的钱省下来了」的权威答案。
你的 SOP-01「按省钱数字报价」需要的就是这套方法。

二、四大核心论点

1. 别只看准确率——要看业务指标

Agent 评估不能只测"模型答对了多少题"，要测：

层级 指标举例
模型层 准确率 / 召回率 / 幻觉率
任务层 完成率 / 平均步数 / 失败重试率
业务层 客户满意度 / 节省时间 / 减少错误
经济层 帮客户省了多少钱 / 提升多少产能

对应你 SOP-01 第 3 步"按省钱数字报价"——
业务指标 + 经济指标才是真评估。

2. 故障注入测试（Failure Injection Testing）

这是和 C2「混沌工程」一脉相承的工程实践。

主动制造异常：
- 给 Agent 一个故意错误的数据，看会不会出错
- 关掉一个工具，看会不会死循环
- 把工具返回结果延迟，看会不会超时
- 模拟用户故意误导，看会不会被骗

目的：不是证明 Agent 多强，是证明 Agent 在异常下不死。

对应你的"知识库项目 7 成是脏活"——故障注入就是最脏的活。

3. 边界验证（Boundary Verification）

Agent 的能力有边界，必须明确标注：

  • 能做：查询 X 库 / 修改 Y 字段 / 调用 Z 工具
  • 不能做：删除生产数据 / 修改客户合同 / 转账超过 X 元
  • 不确定：判断 Y 类型 / 评估 Z 风险

验证方法：用边界 case 测试集，确保"不能做"绝对不做。

对应 SOP-07「报价签约」里的"交付标准"——
必须白纸黑字写清楚 Agent 能做什么、不能做什么。

4. 可验证标准（Verifiable Criteria）

不要用"用户体验更好""效率提升"这种模糊指标。
要换成可量化、可自动测的指标：

❌ 模糊 ✓ 可验证
体验更好 客服响应时长从 30s 降到 5s
效率提升 单据处理从 4 小时降到 30 分钟
更准确 字段抽取准确率从 78% 升到 96%
客户满意 NPS 从 32 升到 58

对应你 SOP-07「报价签约」里的"价值量化"——必须可验证、可对账。

三、关键术语

英文 中文 释义
Failure Injection 故障注入 主动制造异常验证护栏
Boundary Verification 边界验证 明确 Agent 能/不能做什么
Verifiable Criteria 可验证标准 可量化的评估指标
Business Metric 业务指标 真实业务结果的指标
Task Completion Rate 任务完成率 Agent 完整跑通任务的比率
Step Efficiency 步数效率 完成任务用了多少步

十一、4 层评估指标的计算方法

第 1 层：模型层指标（自动测）

准确率 = 答对数 / 总数
召回率 = 召回正确答案数 / 全部正确答案数
F1 = 2 × 准确率 × 召回率 / (准确率 + 召回率)
幻觉率 = 编造内容数 / 总回答数

自动化：用测试集 + 脚本比对，无需人工。

第 2 层：任务层指标（半自动测）

完成率 = 完整跑通的任务数 / 总任务数
平均步数 = 总步数 / 任务数
失败重试率 = 重试次数 / 总任务数
用户接管率 = 人工介入次数 / 总任务数

半自动：跑真实任务流 + 日志分析。

第 3 层：业务层指标（业务方定义）

客户满意度 = 5 分制平均分
节省时间 = 之前耗时 - 现在耗时
错误率下降 = (之前错误率 - 现在错误率) / 之前错误率

定义权在业务方——FDE 不能拍脑袋。

第 4 层：经济层指标（FDE 自证）

年节省 = Σ(业务流节省的年人时) × 时薪
客单价合理性 = 客户预算 / 年节省（建议 10-20%）
ROI = (年节省 - 项目费) / 项目费 × 100%

自证逻辑：能算清楚 ROI = 报价合理 = 续约有据。

十二、3 个客户说服话术

话术 1：建立评估基线

"在调优之前，我们先建一个 50-100 条的黄金集——
全部来自您真实业务素材，每条带标准答案。
用这个基线测出来 78% 准确率，调完模型升到 96%——
这就是我们的验收标准。"

话术 2：用业务指标不用模型指标

"模型准确率 95% 不等于业务有用——
业务指标是'客服响应时长从 30s 降到 5s'，
这是您能感知、您老板能看懂的指标。"

话术 3：把评估当续约条件

"上线后每月出一份评估报告——
准确率、响应时长、节省金额三项数字。
数据下降就触发模型调优，数据达标就触发续约谈判。"

十一、原文核心（Anthropic 2023 年 10 月原文）

来源：https://www.anthropic.com/research/evaluating-ai-systems （原文 2.4 万字）

1. 核心结论（原文两个 takeaways）

"我们希望读者带走两个核心观点：
1. 健壮的评估极其难以开发和实施
2. 有效的 AI 治理取决于我们有意义地评估 AI 系统的能力"

2. 6 大评估挑战（按难度递增）

挑战 1：Multiple Choice Evaluations（MMLU 等）

Anthropic 发现 MMLU 的 4 个问题：

  1. MMLU 太广为人知，模型训练时可能见过 —— 相当于学生考前看过考题
  2. 简单格式变化可改变 5% 准确率 —— (A) vs (1)，(A) vs [A] 都影响
  3. 实现不一致 —— 有些实验室用 few-shot、CoT 提高 MMLU 分数
  4. MMLU 本身可能有错 —— 找到过 mislabeled 的题目

教训："supposedly simple and standardized evaluation" 实际上需要很多 tricky 判断。

挑战 2：BBQ（社会偏见）

"实施 BBQ 花了一个最好的工程师一整个不间断的周"

Anthropic 真实故事：
- 实施 BBQ 几个月，模型偏见分 = 0
- 内部一位 BBQ 开发者问："你们检查了模型是否在回答问题吗？"
- 结果发现：模型根本没在答 —— 偏见分 0 是因为返回空答案
- "技术上无偏见，但也完全无用"

教训：
- 评估可能完全误导你
- 总是先做sanity check（模型到底在不在答）

挑战 3：BIG-bench（204 个评估的众包集合）

4 个问题：
1. 大量工程量才能装上
2. 跑全部 204 项无法在合理时间完成
3. 发现了 BBQ-lite 实现 bug
4. 决定哪些任务最重要需要研究投入

挑战 4：HELM（斯坦福）

3 个问题：
1. HELM 不支持 Anthropic 的 Human/Assistant 格式 → 误评 Claude
2. 迭代慢 —— 新模型评估要几个月
3. 需要协调和沟通

教训：第三方评估不是中立、免费的午餐。

挑战 5：A/B Testing with Crowdworkers

局限性：
- 贵 + 慢
- 评估者差异大（创造力、动机）
- helpfulness vs harmlessness 的张力
- "What numerical value indicates a model is sufficiently helpful and harmless?"

挑战 6：Frontier Threats Red Teaming（国关级红队）

"国家安全的独特性使评估比一般伤害更有挑战性
——国家安全风险复杂、需要专家级敏感知识、依赖现实场景"

3 个特殊挑战：
1. 国家安全风险是complicated, expert knowledge, real-world
2. 红队是艺术而非科学 —— 还没有标准化
3. 可重复 + 量化很难

3. 用生成式 AI 评估生成式 AI（最有前景）

"我们最有趣的实验：用生成式 AI 开发评估生成式 AI。"

做法：
- 用 Claude 帮生成评估数据集
- 用 Claude 帮评分其他模型输出
- 形成评估回路

优势：规模大、速度快、便宜
风险：评估器和被评估模型同样有偏见

4. 政策建议（Anthropic 5 条）

  1. 不要把分数当唯一证据 —— 量化是起点不是终点
  2. 永远做 sanity check —— 模型在答问题吗？
  3. 多种评估结合 —— 不依赖单一 benchmark
  4. 公开评估方法和局限 —— 透明度
  5. 持续投入评估能力 —— 不只是模型

5. 与企业 FDE 项目的映射

Anthropic 挑战 FDE 项目应对
MMLU 训练泄露 评测集必须100% 来自客户真实业务，不是公开数据集
格式敏感 同一格式跑全评测，不中途改 prompt
BBQ 空答案问题 每条评测都人工 spot-check 一次
第三方评估错位 自建评测，按业务定制
A/B testing 贵 用黄金集 + 自动化脚本
红队是艺术 客户业务方做 red team，比通用 red teamer 更准
生成式评估有偏见 多个 AI 互审 + 人工兜底

十二、客户讨论话术

"Anthropic 官方说：'Robust evaluations are extremely difficult to develop and implement'。

这就是为什么我们的评测集不直接用 MMLU——而是用客户的真实业务素材建 50-100 条黄金集。

我们每条评测都做人工 sanity check——确保模型在答问题，
不是在 BB（Bullshit）一个 0 分的'无偏见'答案。"

"Anthropic 的 BBQ 团队就栽过这跟头：
模型偏见分 0 = 模型根本没在答问题。
我们的评测避开了这个陷阱。"
