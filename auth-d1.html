D1 · Google Agent Design Framework

类型：行业权威框架 · 厂商标准
发布：Google（与 Vertex AI Agent Builder 配套）
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

Google 的 Agent 设计框架是 A2（Anthropic 生产级 Agent 白皮书）的最有力同行——
两家从不同工程传统出发，但收敛到同一套方法论。

你的方法论「按价值付费」「风险分级」就是这两家厂商共同验证过的标准。

二、四大核心论点

1. Agent 动作白名单（Action Allowlist）

不是"AI 能做什么"开放给所有动作，而是白名单制：

  • 每个 Agent 在创建时定义允许调用的工具列表
  • 任何工具调用超出白名单 → 自动拒绝
  • 修改白名单需要人工审批

对应 A2「生产级 Agent 白皮书」的 Action Boundary——
白名单比黑名单安全（默认拒绝 vs 默认放行）。

2. 风险分级 + 人机交接（Human Handoff）

Google 的分级（和 A2 类似但措辞不同）：

风险级 名称 处理
Low 只读 AI 自动
Medium 写但可逆 AI 自动 + 通知
High 写且难逆 AI 提交 + 人工确认
Critical 不可逆 必须人工执行

人机交接的关键：
- 不是所有事都让 AI 做
- 高风险动作必须有人"接最后一棒"
- 交接信息要完整（AI 把上下文打包好给人工）

对应你的 SOP-03 第 3 步"立刚性规则"——

3. 评估体系（Evaluation Harness）

Google 的评估三件套：

评估类型 做什么 频率
Offline Eval 跑测试集，看准确率 每次发版前
Online Eval 线上 A/B，对比业务指标 持续
Human Eval 专家打分 每周抽检

关键指标：
- 任务完成率
- 平均步数
- 用户满意度
- 工具调用错误率
- 人工接管率（越低越好，但 0 不正常）

对应 A3「企业 Agent 评估」——

4. Agent 系统的可观测性（Observability）

Google 把 Agent 当分布式系统看，要求：

  • Trace：每个请求的完整调用链
  • Metrics：延迟、错误率、Token 消耗
  • Logs：结构化日志，可搜索
  • Alerts：异常自动告警

工具：Cloud Trace + Cloud Monitoring + Looker

对应 B1「Building LLM Apps」的论点 4——

三、与 Anthropic 框架的对比

维度 Google Anthropic 共识
工具管理 白名单 边界 都强调限制
风险分级 4 级（Low/Med/High/Crit） 5 级（L0-L4） 一致
评估 三件套 4 层指标 一致
可观测 Cloud 工具链 自建 Trace 概念一致
工程化 Vertex AI 平台 Claude API + SDK 路径不同

对你最有价值的洞察：

两家头部厂商的方法论收敛到同一套——
说明这套方法论不是某家厂商的偏好，是行业共识。
见客户时引用两家说法，分量翻倍。

十一、工具白名单的工程实现

实现 1：JSON Schema 定义

{
  "allowed_tools": [
    {
      "name": "search_docs",
      "tier": "L0",
      "description": "搜索内部文档库"
    },
    {
      "name": "send_email",
      "tier": "L2",
      "requires_confirmation": true,
      "description": "发送邮件给客户"
    },
    {
      "name": "delete_record",
      "tier": "L4",
      "requires_double_confirmation": true,
      "forbidden_in_auto_mode": true
    }
  ]
}

实现 2：调用前校验

def invoke_tool(tool_name, params):
    if tool_name not in ALLOWED_TOOLS:
        reject("Tool not in whitelist")
    tool = ALLOWED_TOOLS[tool_name]
    if tool['tier'] >= 'L3' and not human_confirmed:
        return require_human_confirmation()
    return execute(tool, params)

实现 3：白名单变更审批

变更类型 审批人 周期
新增 L0-L1 工具 FDE 主管 即时
新增 L2 工具 业务负责人 + IT 1 天
新增 L3-L4 工具 CISO + 业务负责人 + IT 1 周

十二、3 个常见反模式

反模式 1：白名单过于宽松

症状：所有工具都在白名单里。
风险：等于没白名单。
正解：只放真正常用的，其他需要审批。

反模式 2：白名单变更无审批

症状：开发者直接加新工具。
风险：未经评估的高危工具上线。
正解：分级审批（按工具 tier）。

反模式 3：白名单写在代码里

症状：白名单是 Python dict 写死的。
风险：改白名单要发版。
正解：白名单放配置文件或数据库，运行时加载。
