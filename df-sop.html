FDE（Forward Deployed Engineer）阶段式 SOP

本文件定位：FDE 岗位的标准作业程序（SOP），采用 7 阶段 × 6 块结构，每个阶段都给出权威标准映射、FDE 关键动作、工具栈、检查表、反模式，并附关键术语锚链指向《专业大词典》A/B/C 卷与本轮《权威源中文提取》。

核心哲学（来自 Anthropic FDE 一手源 citation:Anthropic FDE Blog 2024）：
1. 业务指标优先——用业务 KPI 验收，不用模型 benchmark。
2. 驻场共创——去客户现场结对写代码，不远程"顾问咨询"。
3. 平台-产品反哺——现场沉淀回 Harness/Skill/护栏。
4. 风险驱动（来自《Software Architecture: Foundations, Theory, and Practice》）——架构决策由风险驱动，没有风险就不引入组件，避免过度工程。

阶段 1：需求阶段（Discovery & Framing）

1.1 阶段目标

将客户业务需求转化为可建模、可验收、可证伪的技术规格。FDE 进场首要工作不是写代码，而是理解业务。

1.2 权威标准映射

  • SWEBOK V4 需求域（Requirements Engineering） citation:SWEBOK V4：需求获取、分析、规格说明、确认、变更管理 [术语: 需求工程] [SOP: 需求阶段]。
  • PMBOK 7th 干系人绩效域（Stakeholder Performance Domain）：识别关键干系人，管理期望 [术语: 干系人绩效域]。
  • BABOK V3 知识领域（Knowledge Areas）：业务分析、需求生命周期管理、战略分析、解决方案评估 [术语: BABOK] [SOP: 需求阶段]。
  • NIST AI RMF GOVERN：建立风险管理文化、政策、流程 [术语: GOVERN 治理功能]。
  • Anthropic FDE 业务抽象（Business abstraction）：把客户业务翻译为可建模的 Agent 任务。
  • DDD 通用语言 + 战略设计：限界上下文、领域划分（详见本卷 2.3 节 [citation:DDD Eric Evans]）。

1.3 FDE 关键动作

动作 产出 工具/方法
现场访谈（业务专家） 业务蓝图 客户会议、价值流图
价值流分析 VDNA 模型 Value-Domain-Notion-Action 四步法 [术语: VDNA 模型]
业务规则抽取 业务规则文档 用户故事、用例图
限界上下文划分 上下文地图 DDD Event Storming [术语: 限界上下文]
干系人矩阵 干系人登记册 权力/利益矩阵
业务 KPI 定义 KPI 字典 业务成果导向指标
风险初步识别 风险登记册 风险驱动架构 + BABOK 风险分析
需求基线 需求规格说明书 SRS Volere、IEEE 830

1.4 工具栈推荐

  • 协作：Notion、Confluence、飞书、Obsidian。
  • 建模：Miro、Whimsical、Draw.io（UML / 流程图 / 上下文图）。
  • Event Storming：Miro + 便利贴远程协作。
  • 访谈录音转写：通义听悟、Whisper。
  • 用户画像：Persona 模板。
  • 需求管理：Jira、Linear、Azure DevOps。

1.5 检查表

  • ✅ 客户业务目标可一句话表达
  • ✅ 至少 3 位业务专家访谈完成
  • ✅ VDNA 四要素全部填写
  • ✅ 限界上下文图绘制完成
  • ✅ 业务 KPI 已量化（带基线值）
  • ✅ 风险登记册已建立
  • ✅ 干系人已分类，关键决策人识别
  • ✅ 通用语言表（中文/英文/业务术语）已建立
  • ✅ POC vs Production 边界已明确（来自 citation:Anthropic FDE Blog 2024）

1.6 常见反模式

  • ❌ 远程写需求：不驻场，靠文档沟通需求 → 100% 失真。
  • ❌ 技术驱动需求：先选模型再找场景。
  • ❌ 一上来建表：不划分限界上下文直接建数据模型。
  • ❌ 需求大爆炸：一次性写 200 个用户故事而不分优先级。
  • ❌ 混淆 demo 与交付：用 demo 替代 SRS。
  • ❌ 忽略合规：金融、医疗等强监管行业未识别合规风险。
  • ❌ 业务专家缺席：FDE 自己脑补业务逻辑。

阶段 2：设计阶段（Architecture & Risk Modeling）

2.1 阶段目标

基于需求和已识别风险，设计最小可行架构 + 完整防护矩阵。FDE 的设计哲学是"风险驱动 + 可逆优先"。

2.2 权威标准映射

  • SWEBOK V4 设计域（Software Design）：架构设计、详细设计、接口设计、模式 [术语: 软件设计域] [SOP: 设计阶段]。
  • TOGAF 10 ADM 阶段 A-D：架构愿景、业务架构、信息系统架构、技术架构 [术语: TOGAF ADM]。
  • ArchiMate 3.2：业务、应用、技术三层架构建模 [术语: ArchiMate]。
  • NIST AI RMF MAP（Map 映射）：建立框架识别风险、上下文映射 [术语: MAP 映射功能]。
  • Adele Lin《Designing Agentic Systems》：Harness 设计、Skill 封装、约束框架。
  • Pete Hunt 模型网关：Middle 网关 + 限流 + 鉴权 + 缓存。
  • Risk-Driven Architecture：组件由风险驱动。
  • DDD 战术设计：实体、值对象、聚合、领域事件、领域服务。

2.3 FDE 关键动作

动作 产出 方法
风险驱动架构评审 决策矩阵 + 组件清单 风险 × 组件映射表（详见本卷 §2.1）
架构愿景文档 架构愿景图 + ADR TOGAF ADM A
限界上下文细化 上下文地图 TOGAF ADM B + DDD 战术
Harness 设计 Harness 设计规格 Anthropic 三要素（循环/状态/终止）[术语: Harness 执行容器]
Skill 库设计 Skill 清单 + Schema Adele Lin 原子性/可描述/可版本化三原则 [术语: Skill]
Middle 网关设计 网关规格 + 路由表 Pete Hunt 七大能力 [术语: 模型网关]
工具风险分级 Tool Risk Tiering Adele Lin L0-L4 [术语: 工具风险分级]
HITL 策略 HITL 策略文档 高风险动作定义 [术语: HITL]

2.4 工具栈推荐

  • 架构建模：Archi、Draw.io、Structurizr（C4）、PlantUML。
  • 协作：Miro、Notion ADR 模板。
  • 决策记录：MADR、Nygard ADR 模板。
  • 威胁建模：OWASP Threat Dragon、Microsoft Threat Modeling Tool。
  • 架构评估：ATAM（架构贸易分析）、CBAM。

2.5 检查表

  • ✅ 风险矩阵已建立，每条风险对应防护组件
  • ✅ 不可逆动作已识别（L3-L4）
  • ✅ Harness 三要素（执行循环/状态/终止）已设计
  • ✅ Skill 库 Schema 已定义（输入/输出/错误）
  • ✅ 网关七大能力已设计（路由/限流/鉴权/缓存/降级/审计/A/B）
  • ✅ HITL 策略文档已发布
  • ✅ 业务回滚函数已设计（不是模型回滚）
  • ✅ 决策可逆性已评估（提示词 vs 微调 vs 基础设施）
  • ✅ RAG 决策矩阵已应用（何时上/不上）
  • ✅ 评估指标字典已建立（业务/任务/合规/性能 4 类）
  • ✅ ADR 已记录所有关键架构决策
  • ✅ YAGNI 已确认（未引入无风险组件）

2.6 常见反模式

  • ❌ 组件大爆炸：堆 20 个组件应对未发生的风险。
  • ❌ 只设计模型回滚：忽略业务回滚（Anthropic 重点警示）。
  • ❌ HITL 一刀切：要么全开要么全关。
  • ❌ Skill 设计成万能函数：违反原子性原则。
  • ❌ 无决策记录：架构决策口口相传，无 ADR。
  • ❌ 不可逆决策草率：微调、SFT、合同等不可逆决策未经评审。
  • ❌ 过度设计 RAG：通用场景强行上 RAG 导致成本失控。

阶段 3：实现阶段（Build & Encode）

3.1 阶段目标

将设计转化为可运行代码：Harness 编码、Skill 编码、Tool 实现、Prompt 版本化、单元测试通过。

3.2 权威标准映射

  • SWEBOK V4 构造域（Construction）：编码、测试、重构、集成 [术语: 软件构造域] [SOP: 实现阶段]。
  • ISO/IEC/IEEE 12207:2017 实现过程：实现活动、单元测试、集成测试。
  • Anthropic《Building agents for production》：Harness 编码、护栏编码。
  • Adele Lin 编排范式：ReAct、Plan-and-Execute、Reflexion、Multi-Agent。
  • Pete Hunt 编码实践：限流、缓存、A/B。
  • NIST AI RMF MANAGE：风险管理资源配置、MLOps 落地。

动作 产出 方法

3.4 工具栈推荐

  • 代码：Python（LangChain/LlamaIndex/AutoGen）、TypeScript（Vercel AI SDK）、Go、Java（Spring AI）。
  • Agent 框架：LangGraph、AutoGen、CrewAI、DSPy。
  • Skill 库：Adele Lin 风格原子函数 + Schema。
  • Prompt 管理：PromptFoo、PromptLayer、Helicone。
  • 版本控制：Git + Conventional Commits + GitFlow。
  • CI：GitHub Actions、GitLab CI、CircleCI。
  • 测试：Pytest、JUnit、Testcontainers。
  • 代码质量：SonarQube、Snyk、Ruff、ESLint。

3.5 检查表

  • ✅ Harness 三要素全部编码
  • ✅ 每个 Skill 有版本号 + Schema + 单元测试
  • ✅ 每个 Tool 有风险等级标记 + 单元测试
  • ✅ Prompt 有版本管理 + 变量化
  • ✅ 状态管理三级（短期/中期/长期）已实现
  • ✅ HITL 切换已实现并测试
  • ✅ 业务回滚函数已实现并测试
  • ✅ Middle 网关七能力全部落地
  • ✅ 单元测试覆盖率 ≥ 80%
  • ✅ 集成测试通过
  • ✅ 代码已通过 PR 评审 + SonarQube
  • ✅ SBOM 已生成（[术语: SBOM]）

3.6 常见反模式

  • ❌ Tool 写成万能函数：违反 Adele Lin 原子性。
  • ❌ Prompt 硬编码：不变量化、不可版本化。
  • ❌ 无状态管理：Agent 状态全靠上下文窗口，跨会话失忆。
  • ❌ HITL 写在文档里：没真正实现异步审批流。
  • ❌ 业务回滚缺失：只回 checkpoint 不回业务。
  • ❌ Skill 没有版本号：升级破坏旧调用。
  • ❌ 循环无限：未设最大步数/超时，Agent 失控（Anthropic 警示）。
  • ❌ 绕过 Harness 直接调模型：失去可观测和护栏。

阶段 4：测试阶段（Test & Evaluate）

4.1 阶段目标

建立可证伪的评估体系：离线 + 在线 + 故障注入三件套，让效果/风险/性能可重复测量。

4.2 权威标准映射

  • SWEBOK V4 测试域（Software Testing）：测试策略、技术、度量、管理 [术语: 软件测试域] [SOP: 测试阶段]。
  • NIST AI RMF MEASURE：分析、评估、基准测试 [术语: MEASURE 评估功能]。
  • Anthropic《Evaluating AI agents》：离线 + 在线 + 故障注入。
  • Pete Hunt 评估策略：风险分级 + 评估矩阵。
  • Chaos Engineering（Netflix）：故障注入、稳态假设、最小爆炸半径 [术语: 稳态假设] [术语: 最小爆炸半径]。

7.6 常见反模式

  • ❌ 平台反哺缺失：每个项目从零开始（Anthropic 重点警示）。
  • ❌ 黄金集过时：评估集停留在 6 个月前。
  • ❌ 模型无持续训练：上线即"冻结"。
  • ❌ 复盘走形式：Postmortem 无行动项或行动项不闭环。
  • ❌ 客户关系断档：上线后无健康度跟踪。
  • ❌ 团队能力不培养：FDE 永远是个人英雄。
  • ❌ 漂移无人监控：模型效果恶化无人察觉。
  • ❌ CDSO 停滞：永远在 Level 1/2，不向自动化推进。
  • ❌ SFIA 画像缺失：不知道团队能力在哪一层。

SOP 适用边界

✅ 适用

  • 企业 AI 落地项目（Agent / RAG / LLM 应用）
  • 需要业务驻场交付的 ToB 项目
  • 涉及高风险决策（金融、医疗、法律、自动决策）的场景
  • 多团队协作、多阶段交付的复杂项目

⚠️ 部分适用

  • 纯研究项目（学术、企业研究院）：SOP 偏重，可简化部分阶段。
  • 单人小项目：阶段可合并，但风险驱动与评估不可省。
  • SaaS 自研产品：FDE 部分角色由产品/工程承担，可裁剪。

❌ 不适用

  • 纯算法研究（无业务交付）。
  • 个人兴趣项目。
  • POC-only（无生产目标）——可直接走 POC 流程，不进 SOP。
