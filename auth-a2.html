A2 · 《Building agents for production》Anthropic 生产级 Agent 白皮书

类型：一手权威 · 厂商白皮书
发布：Anthropic（与 A1 同期发布）
链接：anthropic.com / Building agents for production
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

如果说 A1（Anthropic FDE 博客）讲的是 FDE 这个角色，
那 A2 讲的是 FDE 工作的 核心产出物——生产级 Agent 的工程标准。

这篇是「把 Demo 变生产」的权威标准。
客户问"你们的 Agent 怎么保证不出错"，答案就在这里。

二、四大核心论点

1. Harness（执行容器）：Agent 的运行时

Harness 不是 Agent 本身，是包裹 Agent 的容器。它负责：

  • 工具调用路由：决定 Agent 调哪个工具、按什么顺序
  • 状态管理：保存对话历史、中间变量、记忆
  • 动作边界（Action Boundary）：哪些动作可自动、哪些必须人工
  • 故障隔离：单个动作失败不能拖垮整个系统
  • 业务事务回滚：Agent 调了工具之后如果出错，要能"撤销"业务影响

对应你 SOP-03 第 3 步"立刚性规则再谈 AI"——
刚性规则就是 Harness 里的 Action Boundary。

2. 动作护栏（Guardrails）：把"AI 不能做什么"写进代码

不是"AI 应该怎么做"（那是 Prompt），
而是"AI 绝对不能做什么"——用代码硬约束。

典型护栏：
- 金额上限：单笔转账不超过 X 元
- 操作窗口：浇水只能在 8:00-18:00
- 审批前置：删除数据前必须人工确认
- 白名单工具：Agent 只能调用注册的 N 个工具

对应你方法论「接单判断」第 11 条
「AI 只做降门槛，核心执行用确定性规则」——
这就是 Guardrail 的具体形态。

3. 人工接管（Human-in-the-Loop）：高危动作强制确认

不是所有动作 AI 都能自己完成。风险分级是关键：

风险级 动作类型 处理方式
L0 只读 查数据 / 读文档 AI 自动
L1 低危写 改一个字段 / 发一条消息 AI 自动 + 日志
L2 中危写 发邮件 / 创建订单 AI 自动 + 异步通知
L3 高危写 转账 / 删除 / 修改核心数据 AI 提交 + 人工确认
L4 不可逆 关停系统 / 退款 必须人工执行

这套分级是 SOP-07「报价签约」里必须写进合同的交付标准。

4. 状态管理与故障隔离：Agent 不能"半成品"

生产环境 Agent 的状态必须显式可恢复：
- 任何中间步骤的失败都能从断点继续
- 任何动作的影响都能被回滚
- 任何异常都有清晰的错误信号

对应你方法论里反复出现的"留兜底"——这就是工程化的兜底。

十一、Harness 的 5 层工程实现

Anthropic 的 Harness 不只是概念，是具体可实现的 5 层架构：

第 1 层：输入处理（Input Processing）

  • 职责：清洗 / 标准化 / 安全过滤用户输入
  • 工具：Guardrail AI / NeMo Guardrails / 自建正则
  • 代码示例（Python 伪代码）：
def input_layer(user_input):
    sanitized = remove_pii(user_input)
    if detect_prompt_injection(sanitized):
        return reject("Potential injection detected")
    return add_context(sanitized)

第 2 层：路由层（Routing）

  • 职责：决定哪个 Agent / 工具 / 模型处理
  • 工具：LangChain Router / LlamaIndex Router
  • 决策维度：意图分类 / 风险分级 / 成本预算

第 3 层：Agent 核心

  • 职责：推理 + 工具调用 + 规划
  • 工具：Claude / GPT / 自研 Agent
  • 状态：会话 / 任务 / 业务 / 记忆

第 4 层：动作执行（Action Execution）

  • 职责：调用工具 / 写数据库 / 调 API
  • 关键：必须有事务回滚机制（Saga 模式）

第 5 层：输出处理 + 审计

  • 职责：结果校验 / 审计日志 / 用户通知
  • 关键：所有动作留痕，可追溯

十二、4 个常见反模式

反模式 1：裸调模型

症状：直接调 OpenAI API，没 Harness。
风险：无护栏、无审计、无法回滚。
正解：加 5 层 Harness。

反模式 2：护栏写在 Prompt 里

症状：「请不要做 X」写在 system prompt。
风险：模型可能忽略（幻觉 / 注入）。
正解：护栏写进代码（输入校验 + 输出过滤 + 动作拦截）。

反模式 3：所有动作都让 AI 自动

症状：转账 / 删除数据也自动执行。
风险：高危动作一旦出错，损失不可逆。
正解：L0-L4 风险分级，L3-L4 强制人工确认。

反模式 4：忽略业务回滚

症状：Agent 调用了工具但失败了，业务影响没撤销。
风险：数据库脏数据 / 用户收到错误邮件。
正解：Saga 模式 + 补偿事务 + 软删除。

十一、原文核心（Anthropic 2024 年 12 月原文）

来源：https://www.anthropic.com/engineering/building-effective-agents （原文 2 万字）

1. Agents vs Workflows 的关键区分

Anthropic 把所有 agentic systems 分两类：

类别 特征 适合场景
Workflows LLM 和工具通过预定义代码路径编排 任务明确、可分解
Agents LLM 动态指导自己的流程和工具使用 灵活性 + 模型决策

"Anthropic 内部把这两类都归为 agentic systems，但画了清晰的架构界限。"

2. 何时用 / 何时不用 agents

Anthropic 原文原话：

"我们建议找到最简的解决方案，只在需要时增加复杂度。
这可能意味着完全不要构建 agentic 系统。
Agentic systems 经常用延迟和成本换取更好的任务性能，
你应该考虑这种 trade-off 何时合理。"

判断矩阵：

场景 用什么 原因
单次 LLM 调用 + 检索 + 上下文示例 不用 agent 已足够
任务明确 + 可分解 Workflow 稳定
需要灵活决策 Agent 灵活
成本 / 延迟敏感 不用 agent 代价大

3. 5 种 Workflow 模式（核心！）

模式 1：Prompt Chaining（提示链）

  • 结构：LLM 调用序列 + 中间检查（gate）
  • 何时用：任务能清晰分解为固定子任务
  • 例子：营销文案 → 翻译成另一语言；写文档大纲 → 检查 → 写正文

模式 2：Routing（路由）

  • 结构：分类器把输入路由到专门的处理流
  • 何时用：任务有明确不同类别
  • 例子：客服查询分类（普通 / 退款 / 技术支持）；简单问题用 Claude Haiku、难问题用 Claude Sonnet

模式 3：Parallelization（并行化）

  • 结构：LLM 并行处理同一任务的不同部分
  • 两种形式：
  • Sectioning：把任务拆成独立子任务并行
  • Voting：跑同一任务多次取多数票（用于高准确性场景）
  • 例子：多视角内容审核；代码漏洞检测

模式 4：Orchestrator-Workers（编排者-工人）

  • 结构：中央 LLM 动态分解任务、委派给 worker LLM、整合结果
  • 何时用：无法预测所需子任务
  • 例子：需要修改多个文件的代码项目；多源信息检索

模式 5：Evaluator-Optimizer（评估者-优化者）

  • 结构：一个 LLM 生成输出，另一个 LLM 评估并提供反馈，循环
  • 何时用：有明确评估标准、迭代改进有价值
  • 例子：文学翻译（评估者给多轮反馈）；复杂搜索（评估者决定信息够不够）

4. Autonomous Agents（自主智能体）

Anthropic 区分 agent 和 workflow 的关键：
- Workflows 通过预定义路径编排
- Agents 动态指导自己的过程

"Agents 在每一步根据环境反馈决定下一步做什么——
这让它们能处理复杂任务，但代价是更多延迟和成本。"

5. 框架使用建议（重要！）

Anthropic 明确警告：

"我们建议开发者直接用 LLM API起步：
很多模式可以用几行代码实现。
如果用框架，要确保你理解底层代码——
对底层工作原理的错误假设是客户错误的常见来源。"

框架选型：
- 推荐：Claude Agent SDK
- 也可用：Strands Agents SDK (AWS), Rivet, Vellum

6. Augmented LLM（增强 LLM）作为基础构件

所有 agentic systems 的基础构件 = LLM + 检索 + 工具 + 记忆。

"The basic building block of agentic systems is an LLM
enhanced with augmentations such as retrieval, tools, and memory."

实现建议：
- 用 Model Context Protocol (MCP) 集成第三方工具
- 简化的客户端实现
- 提供清晰、有良好文档的接口

7. 组合模式总结

复杂度 模式 用例
低 Augmented LLM 单次调用
中低 Prompt Chaining 翻译 / 大纲→正文
中 Routing 客服分类
中高 Parallelization 多视角审核
高 Orchestrator-Workers 复杂代码
高 Evaluator-Optimizer 文学翻译
最高 Autonomous Agent 开放研究

核心建议：从最简的 Augmented LLM 开始，按需升级。

十二、客户讨论话术

"Anthropic 官方把 agentic systems 分为 5 个 workflow + autonomous agent。
我们的方案选哪一档取决于您的业务复杂度：
- 简单业务：augmented LLM（1 步）
- 中等业务：routing 或 parallelization（3-5 步）
- 复杂业务：orchestrator-workers 或 autonomous agent

不盲目上 agent = 不浪费您的钱。
这是 Anthropic 2024 年官方建议的核心。"

📖 完整中文全文翻译

原文：Building Effective Agents（构建高效的智能体）
作者：Erik Schluntz & Barry Zhang（Anthropic 工程团队）
发布：2024-12-19
原文链接：https://www.anthropic.com/engineering/building-effective-agents
翻译说明：以下为关键章节的完整中文翻译，非摘要，尽量保留原文论证逻辑。

引言

过去一年，我们与数十个团队合作，在多个行业构建 LLM 智能体。一致地，最成功的实现使用的都是简单、可组合的模式，而不是复杂的框架。

"The most successful implementations weren't using complex frameworks or specialized libraries. Instead, they were building with simple, composable patterns."

在这篇文章中，我们分享从客户合作和自建智能体中学到的东西，给开发者提供构建高效智能体的实用建议。

什么是智能体（Agent）？

"Agent" 有几种定义方式。有些客户把 Agent 定义为完全自主的系统，能长时间独立运行、使用各种工具完成复杂任务；另一些人则用这个词指代更规范化的实现，遵循预定义的工作流。

在 Anthropic，我们把所有这些变体统称为 agentic systems（智能体系统），但画出一条重要的架构区分：

  • Workflows（工作流）：LLM 和工具通过预定义的代码路径编排的系统。
  • Agents（智能体）：LLM 动态指导自己的流程和工具使用、掌控如何完成任务的系统。

何时该用、何时不该用智能体

构建 LLM 应用时，我们建议寻找最简单的解决方案，只在需要时增加复杂度。这可能意味着根本不构建智能体系统。

智能体系统通常用延迟和成本换取更好的任务性能，你要考虑这种权衡何时合理。

当需要更多复杂度时：
- Workflow 为定义明确的任务提供可预测性和一致性；
- Agent 在需要灵活性和模型驱动决策的大规模场景下是更好的选择。

但对很多应用来说，用检索和上下文示例优化单次 LLM 调用通常就足够了。

何时以及如何使用框架

有很多框架让智能体系统更容易实现，包括：
- Claude Agent SDK
- AWS 的 Strands Agents SDK
- Rivet（拖拽式 GUI LLM 工作流构建器）
- Vellum（另一个构建和测试复杂工作流的 GUI 工具）

这些框架通过简化调用 LLM、定义和解析工具、链式调用等底层任务来降低上手门槛。但它们常常增加额外的抽象层，掩盖底层的 prompt 和响应，让调试更难。 它们还可能诱导你在简单方案已足够时增加复杂度。

我们建议开发者直接用 LLM API 起步：很多模式可以用几行代码实现。如果你用框架，确保你理解底层代码——对底层工作原理的错误假设是客户错误的常见来源。

基础构件、工作流与智能体

我们从基础构件——增强型 LLM（augmented LLM）——开始，逐步增加复杂度，从简单的组合式工作流到自主智能体。

基础构件：增强型 LLM

智能体系统的基础构件是一个经过增强的 LLM，增强包括检索、工具和记忆。我们当前的模型能主动使用这些能力——生成自己的搜索查询、选择合适的工具、决定保留什么信息。

我们建议关注实现的两个关键方面：把这些能力定制到你的具体用例，以及确保它们为 LLM 提供简单、文档清晰的接口。实现这些增强的一种方式是通过我们最近发布的 Model Context Protocol (MCP)。

工作流 1：Prompt Chaining（提示链）

提示链把任务分解成一系列步骤，每个 LLM 调用处理上一个的输出。你可以在任何中间步骤添加程序化检查（图中的"gate"）确保流程仍在正轨。

  • 何时用：任务能清晰分解为固定子任务时。主要目标是用延迟换取更高准确率——让每个 LLM 调用变成更简单的任务。
  • 例子：生成营销文案 → 翻译成另一种语言；写文档大纲 → 检查大纲 → 基于大纲写正文。

工作流 2：Routing（路由）

路由对输入做分类，并导向专门的后续任务。它实现关注点分离，构建更专门的 prompt。

  • 何时用：复杂任务有明确的不同类别、分类能被 LLM 或传统分类模型准确处理时。
  • 例子：把客服查询（一般问题/退款请求/技术支持）导向不同流程；把简单问题路由给 Claude Haiku 4.5、难题路由给 Claude Sonnet 4.5。

工作流 3：Parallelization（并行化）

LLM 有时能同时处理一个任务的不同部分，再程序化聚合结果。两种关键变体：
- Sectioning（分段）：把任务拆成独立子任务并行运行。
- Voting（投票）：同一任务跑多次，取多样化输出。

  • 何时用：子任务可并行提速，或需要多视角/多次尝试以获得更高置信度结果时。
  • 例子：
  • 分段：一个模型实例处理用户查询、另一个筛查不当内容（比让同一次调用同时处理护栏和核心响应更好）；自动化评估时每个 LLM 调用评估不同维度。
  • 投票：多个不同 prompt 审查同一段代码漏洞；多个 prompt 评估内容是否不当、设定不同投票阈值。

工作流 4：Orchestrator-Workers（编排者-工人）

中央 LLM 动态分解任务、委派给 worker LLM、综合结果。

  • 何时用：复杂任务无法预知所需子任务时（比如编码中要改的文件数量、每个文件的改动性质取决于任务本身）。与并行化的关键区别是灵活性——子任务不是预定义的，而是编排者根据具体输入决定的。
  • 例子：每次都改动多个文件的编码产品；需要从多个来源搜集分析信息的搜索任务。

工作流 5：Evaluator-Optimizer（评估者-优化者）

一个 LLM 调用生成响应，另一个提供评估和反馈，形成循环。

  • 何时用：有明确评估标准、迭代优化带来可衡量价值时。两个好的契合信号：① 人类反馈能让 LLM 响应明显改善；② LLM 能提供这样的反馈。
  • 例子：文学翻译（译者 LLM 一开始捕捉不到细微之处、评估者 LLM 能提供有用批评）；需要多轮搜索分析的复杂搜索任务。

智能体（Agents）

随着 LLM 在理解复杂输入、推理规划、可靠使用工具、错误恢复等关键能力上成熟，智能体开始在生产中出现。

智能体从一个命令或与人类用户的交互讨论开始。任务清晰后，智能体独立规划运作，可能返回人类获取更多信息或判断。执行期间，智能体在每一步从环境获取"ground truth"（如工具调用结果或代码执行）以评估进展至关重要。智能体可以在检查点或遇到阻碍时暂停等待人类反馈。任务常在完成时终止，但通常会加入停止条件（如最大迭代次数）以保持控制。

智能体能处理复杂任务，但实现往往简单——它们通常只是基于环境反馈在循环中使用工具的 LLM。因此，清晰周到地设计工具集及其文档至关重要。

  • 何时用：开放式问题、难以预测所需步数、无法硬编码固定路径时。智能体可能运行很多轮，你需要对它的决策有一定信任。
  • 成本与风险：自主性意味着更高成本、错误可能复合。建议在沙箱环境大量测试 + 适当护栏。

组合与定制这些模式

这些构件不是规定性的。它们是常见模式，开发者可以塑造和组合以适应不同用例。成功的关键（与任何 LLM 功能一样）是衡量性能并迭代实现。重复一遍：只有在能明显改善结果时才增加复杂度。

总结

"Success in the LLM space isn't about building the most sophisticated system. It's about building the right system for your needs."

构建智能体时，我们尽量遵循三个核心原则：
1. 保持设计的简洁（Maintain simplicity）
2. 通过显式展示规划步骤来优先透明度（Prioritize transparency）
3. 通过彻底的工具文档和测试精心打造 agent-computer interface (ACI)

框架能帮你快速上手，但不要犹豫在生产中减少抽象层、用基础组件构建。遵循这些原则，你就能创建不仅强大、而且可靠、可维护、受用户信任的智能体。

附录 1：智能体实战（两大高价值场景）

A. 客服支持（Customer Support）

客服结合熟悉的聊天机器人界面 + 工具集成增强能力。适合开放式智能体，因为：
- 支持交互天然遵循对话流，同时需要访问外部信息和动作；
- 工具可集成拉取客户数据、订单历史、知识库文章；
- 退款、更新工单等动作可程序化处理；
- 成功可通过用户定义的解决率清晰衡量。

B. 编码智能体（Coding Agents）

  • 代码方案可通过自动化测试验证；
  • 智能体可用测试结果作为反馈迭代方案；
  • 问题空间定义清晰、结构化；
  • 输出质量可客观衡量。

我们自己的实现现在能仅凭 PR 描述解决 SWE-bench Verified 中的真实 GitHub issue。但自动化测试验证功能的同时，人类审查仍对确保方案符合更广泛系统需求至关重要。

附录 2：工具提示工程（Prompt Engineering your Tools）

给工具定义和规格与整体 prompt 同等重视的提示工程关注。

工具格式建议：
- 给模型足够的 token 在"把自己逼进死胡同"前思考；
- 保持格式接近模型在互联网文本中自然见过的样子；
- 确保没有格式"开销"（如需要精确计数数千行代码、或对代码做字符串转义）。

一个经验法则：想想你在人机界面（HCI）上投入了多少精力，就计划在创建好的 agent-computer interface (ACI) 上投入同样多的精力。

ACI 设计建议：
- 站在模型的角度想——基于描述和参数，用这个工具是否显而易见？
- 好的工具定义常包含示例用法、边界情况、输入格式要求、与其它工具的清晰边界；
- 像给团队初级开发者写优秀 docstring 一样改参数名和描述；
- 用 workbench 跑大量示例输入，看模型犯什么错，迭代；
- Poka-yoke（防呆）你的工具——改参数让犯错更难。

在构建 SWE-bench 智能体时，我们花在优化工具上的时间比整体 prompt 还多。例如，我们发现模型在 agent 离开根目录后会用相对路径的工具出错，于是把工具改成始终要求绝对路径——模型从此完美使用。
