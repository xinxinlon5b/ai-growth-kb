A2 · 《Building agents for production》Anthropic 生产级 Agent 白皮书

类型：一手权威 · 厂商白皮书
发布：Anthropic（与 A1 同期发布）
链接：anthropic.com / Building agents for production
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

如果说 A1（Anthropic FDE 博客）讲的是 FDE 这个角色，
那 A2 讲的是 FDE 工作的 核心产出物——生产级 Agent 的工程标准。

这篇是「把 Demo 变生产」的权威标准。
客户问"你们的 Agent 怎么保证不出错"，答案就在这里。

二、四大核心论点

1. Harness（执行容器）：Agent 的运行时

Harness 不是 Agent 本身，是包裹 Agent 的容器。它负责：

  • 工具调用路由：决定 Agent 调哪个工具、按什么顺序
  • 状态管理：保存对话历史、中间变量、记忆
  • 动作边界（Action Boundary）：哪些动作可自动、哪些必须人工
  • 故障隔离：单个动作失败不能拖垮整个系统
  • 业务事务回滚：Agent 调了工具之后如果出错，要能"撤销"业务影响

对应你 SOP-03 第 3 步"立刚性规则再谈 AI"——
刚性规则就是 Harness 里的 Action Boundary。

2. 动作护栏（Guardrails）：把"AI 不能做什么"写进代码

不是"AI 应该怎么做"（那是 Prompt），
而是"AI 绝对不能做什么"——用代码硬约束。

典型护栏：
- 金额上限：单笔转账不超过 X 元
- 操作窗口：浇水只能在 8:00-18:00
- 审批前置：删除数据前必须人工确认
- 白名单工具：Agent 只能调用注册的 N 个工具

对应你方法论「接单判断」第 11 条
「AI 只做降门槛，核心执行用确定性规则」——
这就是 Guardrail 的具体形态。

3. 人工接管（Human-in-the-Loop）：高危动作强制确认

不是所有动作 AI 都能自己完成。风险分级是关键：

风险级 动作类型 处理方式
L0 只读 查数据 / 读文档 AI 自动
L1 低危写 改一个字段 / 发一条消息 AI 自动 + 日志
L2 中危写 发邮件 / 创建订单 AI 自动 + 异步通知
L3 高危写 转账 / 删除 / 修改核心数据 AI 提交 + 人工确认
L4 不可逆 关停系统 / 退款 必须人工执行

这套分级是 SOP-07「报价签约」里必须写进合同的交付标准。

4. 状态管理与故障隔离：Agent 不能"半成品"

生产环境 Agent 的状态必须显式可恢复：
- 任何中间步骤的失败都能从断点继续
- 任何动作的影响都能被回滚
- 任何异常都有清晰的错误信号

对应你方法论里反复出现的"留兜底"——这就是工程化的兜底。

十一、Harness 的 5 层工程实现

Anthropic 的 Harness 不只是概念，是具体可实现的 5 层架构：

第 1 层：输入处理（Input Processing）

  • 职责：清洗 / 标准化 / 安全过滤用户输入
  • 工具：Guardrail AI / NeMo Guardrails / 自建正则
  • 代码示例（Python 伪代码）：
def input_layer(user_input):
    sanitized = remove_pii(user_input)
    if detect_prompt_injection(sanitized):
        return reject("Potential injection detected")
    return add_context(sanitized)

第 2 层：路由层（Routing）

  • 职责：决定哪个 Agent / 工具 / 模型处理
  • 工具：LangChain Router / LlamaIndex Router
  • 决策维度：意图分类 / 风险分级 / 成本预算

第 3 层：Agent 核心

  • 职责：推理 + 工具调用 + 规划
  • 工具：Claude / GPT / 自研 Agent
  • 状态：会话 / 任务 / 业务 / 记忆

第 4 层：动作执行（Action Execution）

  • 职责：调用工具 / 写数据库 / 调 API
  • 关键：必须有事务回滚机制（Saga 模式）

第 5 层：输出处理 + 审计

  • 职责：结果校验 / 审计日志 / 用户通知
  • 关键：所有动作留痕，可追溯

十二、4 个常见反模式

反模式 1：裸调模型

症状：直接调 OpenAI API，没 Harness。
风险：无护栏、无审计、无法回滚。
正解：加 5 层 Harness。

反模式 2：护栏写在 Prompt 里

症状：「请不要做 X」写在 system prompt。
风险：模型可能忽略（幻觉 / 注入）。
正解：护栏写进代码（输入校验 + 输出过滤 + 动作拦截）。

反模式 3：所有动作都让 AI 自动

症状：转账 / 删除数据也自动执行。
风险：高危动作一旦出错，损失不可逆。
正解：L0-L4 风险分级，L3-L4 强制人工确认。

反模式 4：忽略业务回滚

症状：Agent 调用了工具但失败了，业务影响没撤销。
风险：数据库脏数据 / 用户收到错误邮件。
正解：Saga 模式 + 补偿事务 + 软删除。

十一、原文核心（Anthropic 2024 年 12 月原文）

来源：https://www.anthropic.com/engineering/building-effective-agents （原文 2 万字）

1. Agents vs Workflows 的关键区分

Anthropic 把所有 agentic systems 分两类：

类别 特征 适合场景
Workflows LLM 和工具通过预定义代码路径编排 任务明确、可分解
Agents LLM 动态指导自己的流程和工具使用 灵活性 + 模型决策

"Anthropic 内部把这两类都归为 agentic systems，但画了清晰的架构界限。"

2. 何时用 / 何时不用 agents

Anthropic 原文原话：

"我们建议找到最简的解决方案，只在需要时增加复杂度。
这可能意味着完全不要构建 agentic 系统。
Agentic systems 经常用延迟和成本换取更好的任务性能，
你应该考虑这种 trade-off 何时合理。"

判断矩阵：

场景 用什么 原因
单次 LLM 调用 + 检索 + 上下文示例 不用 agent 已足够
任务明确 + 可分解 Workflow 稳定
需要灵活决策 Agent 灵活
成本 / 延迟敏感 不用 agent 代价大

3. 5 种 Workflow 模式（核心！）

模式 1：Prompt Chaining（提示链）

  • 结构：LLM 调用序列 + 中间检查（gate）
  • 何时用：任务能清晰分解为固定子任务
  • 例子：营销文案 → 翻译成另一语言；写文档大纲 → 检查 → 写正文

模式 2：Routing（路由）

  • 结构：分类器把输入路由到专门的处理流
  • 何时用：任务有明确不同类别
  • 例子：客服查询分类（普通 / 退款 / 技术支持）；简单问题用 Claude Haiku、难问题用 Claude Sonnet

模式 3：Parallelization（并行化）

  • 结构：LLM 并行处理同一任务的不同部分
  • 两种形式：
  • Sectioning：把任务拆成独立子任务并行
  • Voting：跑同一任务多次取多数票（用于高准确性场景）
  • 例子：多视角内容审核；代码漏洞检测

模式 4：Orchestrator-Workers（编排者-工人）

  • 结构：中央 LLM 动态分解任务、委派给 worker LLM、整合结果
  • 何时用：无法预测所需子任务
  • 例子：需要修改多个文件的代码项目；多源信息检索

模式 5：Evaluator-Optimizer（评估者-优化者）

  • 结构：一个 LLM 生成输出，另一个 LLM 评估并提供反馈，循环
  • 何时用：有明确评估标准、迭代改进有价值
  • 例子：文学翻译（评估者给多轮反馈）；复杂搜索（评估者决定信息够不够）

4. Autonomous Agents（自主智能体）

Anthropic 区分 agent 和 workflow 的关键：
- Workflows 通过预定义路径编排
- Agents 动态指导自己的过程

"Agents 在每一步根据环境反馈决定下一步做什么——
这让它们能处理复杂任务，但代价是更多延迟和成本。"

5. 框架使用建议（重要！）

Anthropic 明确警告：

"我们建议开发者直接用 LLM API起步：
很多模式可以用几行代码实现。
如果用框架，要确保你理解底层代码——
对底层工作原理的错误假设是客户错误的常见来源。"

框架选型：
- 推荐：Claude Agent SDK
- 也可用：Strands Agents SDK (AWS), Rivet, Vellum

6. Augmented LLM（增强 LLM）作为基础构件

所有 agentic systems 的基础构件 = LLM + 检索 + 工具 + 记忆。

"The basic building block of agentic systems is an LLM
enhanced with augmentations such as retrieval, tools, and memory."

实现建议：
- 用 Model Context Protocol (MCP) 集成第三方工具
- 简化的客户端实现
- 提供清晰、有良好文档的接口

7. 组合模式总结

复杂度 模式 用例
低 Augmented LLM 单次调用
中低 Prompt Chaining 翻译 / 大纲→正文
中 Routing 客服分类
中高 Parallelization 多视角审核
高 Orchestrator-Workers 复杂代码
高 Evaluator-Optimizer 文学翻译
最高 Autonomous Agent 开放研究

核心建议：从最简的 Augmented LLM 开始，按需升级。

十二、客户讨论话术

"Anthropic 官方把 agentic systems 分为 5 个 workflow + autonomous agent。
我们的方案选哪一档取决于您的业务复杂度：
- 简单业务：augmented LLM（1 步）
- 中等业务：routing 或 parallelization（3-5 步）
- 复杂业务：orchestrator-workers 或 autonomous agent

不盲目上 agent = 不浪费您的钱。
这是 Anthropic 2024 年官方建议的核心。"
