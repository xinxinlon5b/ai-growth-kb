B1 · 《Building LLM Applications for Production》Pete Hunt

类型：工程技术书 · Hugging Face 核心工程师
链接：Hugging Face / O'Reilly 渠道可查
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

Pete Hunt 是 React 早期核心贡献者 + Hugging Face 团队负责人。
这本书讲的是 从原型到生产的最后一公里——

"原型能跑 ≠ 生产能用"
这本书就是解决这个 gap 的工程手册。

二、五大核心论点

1. 什么时候上 RAG，什么时候不用

场景 推荐 原因
知识频繁更新 ✓ RAG 模型重训成本高
数据是公司私有 ✓ RAG 不能喂给基础模型
答案必须可追溯 ✓ RAG 能引用原文
通用知识问答 ✗ 不需要 RAG 模型本身够
实时信息查询 ✗ 不建议 RAG 用搜索 API 更准
计算密集任务 ✗ 不需要 RAG 直接调工具

对应你 SOP-07「报价签约」里的"知识库项目 7 成是脏活"——
脏活的本质就是 RAG 的数据准备。

2. 模型网关（Middle Gateway）架构

不是每个业务都直接调 OpenAI API，是调模型网关。网关负责：

  • 路由：哪个请求走哪个模型（GPT-4 / Claude / 本地模型）
  • 限流：防刷、防滥用、配额管理
  • 鉴权：API Key 管理、用户级别权限
  • 缓存：相同问题直接返回缓存，省钱
  • 降级：主模型挂了切备用
  • 日志：所有调用留痕，可观测

对应你方法论「工具链」章 47 条中的多个相关原则——
别直接调模型，加一层网关是基本工程素养。

3. 评估策略 + 风险分级

评估不是"感觉不错"，是分层的：

  • 离线评估：测试集跑分（准确率 / BLEU / 业务指标）
  • 在线评估：A/B 测试，线上对比
  • 人工评估：专家打分，定期抽检
  • 用户反馈：👍👎 一键反馈

风险分级（和 A2 一脉相承）：
- L0 只读：模型随便调
- L1 低危写：限频 + 日志
- L2 高危写：人工抽样审核
- L3 不可逆：必须人工 + 二次确认

4. 可观测（Observability）+ Trace + 日志

生产环境的 LLM 应用必须能回答：

  • 这个请求走了哪条路径？
  • 调了哪个模型？花了多少 token？
  • 每个工具调用花了多长时间？
  • 哪一步出错了？错在哪？

Trace（链路追踪） 是核心工具——把一个请求从入口到出口的全链路画出来。

对应你 SOP-03「FDE 入企交付」第 4 步"留文档"——
Trace 就是"让系统能被人看懂"。

5. 灰度发布 + 版本管理 + 模型回滚

别一次切换 100% 流量：
- 5% 流量试新版本 → 看指标 → 没问题
- 25% → 50% → 100%
- 出问题 1 秒切回老版本

模型版本管理：
- 每个模型版本有明确 ID + 备注
- 不同业务用不同版本（金丝雀）
- 出问题立刻知道是哪个版本

对应你 SOP-04「Agent 工具链自用」第 3 步"给 AI 立硬规则"——
agents.md 写的版本/回滚规则就是这套思想。

十二、3 个常见反模式

反模式 1：每个业务直接调 OpenAI

症状：5 个业务 5 个 API Key 直接调。
风险：成本失控 / 配额散落 / 无法审计。
正解：所有请求经 Middle Gateway。

反模式 2：把缓存当优化

症状：相同问题直接返缓存结果。
风险：用户拿到过期信息（特别是带时间的查询）。
正解：缓存带 TTL，或按查询类型分级缓存。

反模式 3：灰度发布没回滚

症状：新模型直接 100% 流量。
风险：出问题全量影响。
正解：5% → 25% → 50% → 100%，1 秒回滚。

十一、原文核心（Continuous Delivery for ML · CD4ML · Martin Fowler）

来源：https://martinfowler.com/articles/cd4ml.html （53,037 字原文核心）

1. CD4ML 的 3 大原则（原文）

"The principles are the same as for any software system: feedback, repetition, and automation.
But implementing them in machine learning systems requires understanding the unique challenges
of these systems."

CD4ML 3 大原则：
1. Feedback（反馈）：快速、持续的反馈循环
2. Repetition（重复）：可重复的流程
3. Automation（自动化）：消除手工步骤

2. ML 系统的 4 个独特挑战

"Unlike traditional software, ML systems have unique challenges:
- Data dependencies（数据依赖）：模型行为依赖训练数据
- Model decay（模型衰减）：模型性能随时间下降
- Reproducibility（可复现性）：相同代码 + 不同数据 = 不同模型
- Computational intensity（计算密集）：训练成本高"

3. CD4ML 的 8 大组件

# 组件 作用
1 Source Code 代码版本管理
2 Data Versioning 数据版本管理（DVC / Delta Lake）
3 Model Training 自动化训练流水线
4 Model Evaluation 自动化评测
5 Model Packaging 模型打包（Docker / ONNX）
6 Model Serving 模型部署（K8s / vLLM）
7 Monitoring 监控告警（数据漂移 / 性能退化）
8 Feedback Loop 反馈收集 → 触发再训练

4. 与企业 LLM 应用的关系

LLM 应用 = CD4ML 原则 + LLM 特殊考虑：

CD4ML 原则 LLM 应用对应
Feedback 用户反馈 / 评分 / 行为
Repetition Prompt 模板版本化 / Agent 配置版本化
Automation 自动化评测 / 灰度发布 / 回滚

5. 关键工程实践

  • 数据版本化（DVC / Delta Lake）：每次训练绑定具体数据版本
  • 模型注册表（MLflow / Weights & Biases）：模型血缘可追溯
  • 特征工程管线：特征 = 数据 + 转换，特征版本化管理
  • 影子部署（Shadow Deployment）：新模型先在影子环境跑
  • 金丝雀发布（Canary）：5% → 25% → 50% → 100%

6. Pete Hunt 实战建议

Pete Hunt（前 React 核心，Hugging Face 团队）补充：

  • 基础设施优先：先有可复现的环境（Docker / Conda）
  • 小步快跑：不要等"完美模型"，先发布 MVP
  • 可观测性：任何生产事故必须 1 分钟内发现
  • 回滚优先：每次发布必须有回滚预案

7. LLM 应用特有的考虑

  • Token 成本：1 个汉字 ≈ 1.5-2 Token，推理成本必须监控
  • 提示词版本化：Prompt 是"代码"，必须版本管理
  • 缓存策略：相同问题缓存结果，省 Token
  • 多模型路由：不同任务用不同模型（Haiku / Sonnet / Opus）

原文：Continuous Delivery for Machine Learning（CD4ML）
作者：Eric Breck, Shanqing Cai, Eric Nielsen, Michael Salib, D. Sculley
来源：https://martinfowler.com/articles/cd4ml.html

CD4ML 的核心原则

"The principles are the same as for any software system: feedback, repetition, and automation. But implementing them in machine learning systems requires understanding the unique challenges of these systems."

CD4ML 的三原则与任何软件系统相同——反馈（feedback）、重复（repetition）、自动化（automation）。但在机器学习系统中实施它们，需要理解这些系统的独特挑战。

机器学习的三个独特挑战

  1. 数据依赖（Data dependencies）：模型行为依赖训练数据，数据变化会导致模型行为变化；
  2. 模型衰减（Model decay）：模型性能随时间和世界变化而下降；
  3. 可复现性（Reproducibility）：相同代码 + 不同数据 = 不同模型，模型训练本身具有非确定性。

CD4ML 的八组件

# 组件 作用
1 Source Code 代码版本管理
2 Data Versioning 数据版本管理（DVC / Delta Lake）
3 Model Training 自动化训练流水线
4 Model Evaluation 自动化评测
5 Model Packaging 模型打包（Docker / ONNX）
6 Model Serving 模型部署（K8s / vLLM）
7 Monitoring 监控告警（数据漂移 / 性能退化）
8 Feedback Loop 反馈收集 → 触发再训练

关键工程实践

  • 数据版本化：每次训练绑定具体数据版本，保证可复现；
  • 模型注册表：模型血缘可追溯（MLflow / Weights & Biases）；
  • 特征工程管线：特征 = 数据 + 转换，特征版本化管理；
  • 影子部署（Shadow Deployment）：新模型先在影子环境跑，不产生真实影响；
  • 金丝雀发布（Canary）：5% → 25% → 50% → 100%，逐步放量。
