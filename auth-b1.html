B1 · 《Building LLM Applications for Production》Pete Hunt

类型：工程技术书 · Hugging Face 核心工程师
链接：Hugging Face / O'Reilly 渠道可查
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

Pete Hunt 是 React 早期核心贡献者 + Hugging Face 团队负责人。
这本书讲的是 从原型到生产的最后一公里——

"原型能跑 ≠ 生产能用"
这本书就是解决这个 gap 的工程手册。

二、五大核心论点

1. 什么时候上 RAG，什么时候不用

场景 推荐 原因
知识频繁更新 ✓ RAG 模型重训成本高
数据是公司私有 ✓ RAG 不能喂给基础模型
答案必须可追溯 ✓ RAG 能引用原文
通用知识问答 ✗ 不需要 RAG 模型本身够
实时信息查询 ✗ 不建议 RAG 用搜索 API 更准
计算密集任务 ✗ 不需要 RAG 直接调工具

对应你 SOP-07「报价签约」里的"知识库项目 7 成是脏活"——
脏活的本质就是 RAG 的数据准备。

2. 模型网关（Middle Gateway）架构

不是每个业务都直接调 OpenAI API，是调模型网关。网关负责：

  • 路由：哪个请求走哪个模型（GPT-4 / Claude / 本地模型）
  • 限流：防刷、防滥用、配额管理
  • 鉴权：API Key 管理、用户级别权限
  • 缓存：相同问题直接返回缓存，省钱
  • 降级：主模型挂了切备用
  • 日志：所有调用留痕，可观测

对应你方法论「工具链」章 47 条中的多个相关原则——
别直接调模型，加一层网关是基本工程素养。

3. 评估策略 + 风险分级

评估不是"感觉不错"，是分层的：

  • 离线评估：测试集跑分（准确率 / BLEU / 业务指标）
  • 在线评估：A/B 测试，线上对比
  • 人工评估：专家打分，定期抽检
  • 用户反馈：👍👎 一键反馈

风险分级（和 A2 一脉相承）：
- L0 只读：模型随便调
- L1 低危写：限频 + 日志
- L2 高危写：人工抽样审核
- L3 不可逆：必须人工 + 二次确认

4. 可观测（Observability）+ Trace + 日志

生产环境的 LLM 应用必须能回答：

  • 这个请求走了哪条路径？
  • 调了哪个模型？花了多少 token？
  • 每个工具调用花了多长时间？
  • 哪一步出错了？错在哪？

Trace（链路追踪） 是核心工具——把一个请求从入口到出口的全链路画出来。

对应你 SOP-03「FDE 入企交付」第 4 步"留文档"——
Trace 就是"让系统能被人看懂"。

5. 灰度发布 + 版本管理 + 模型回滚

别一次切换 100% 流量：
- 5% 流量试新版本 → 看指标 → 没问题
- 25% → 50% → 100%
- 出问题 1 秒切回老版本

模型版本管理：
- 每个模型版本有明确 ID + 备注
- 不同业务用不同版本（金丝雀）
- 出问题立刻知道是哪个版本

对应你 SOP-04「Agent 工具链自用」第 3 步"给 AI 立硬规则"——
agents.md 写的版本/回滚规则就是这套思想。

五、客户引用话术

"我们的 LLM 应用不是裸调模型，是经过模型网关 + 链路追踪 + 灰度发布这一整套生产化工程的。
出问题能 1 秒回滚，每个调用都有 trace 可查。
这套做法参照 Pete Hunt 那本《Building LLM Applications for Production》。"
