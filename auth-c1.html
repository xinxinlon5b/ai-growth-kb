C1 · 风险驱动架构设计（Risk-Driven Architecture）

类型：通用软件架构方法论
来源：《Software Architecture: Foundations, Theory, and Practice》
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

这是最反"AI 一上来就上架构"的方法论——
架构决策由风险驱动，不是由"听起来高级"驱动。

你的方法论「工具是 0，业务才是 1」就是这套思想的本地化表达。

二、核心论点

1. 架构组件不是越多越好

反模式（企业 AI 项目常见）：
- 上来就搭微服务
- 上来就接向量数据库
- 上来就上 K8s
- 上来就搞多模态
- 上来就搞 AutoML

正解：
- 先识别风险是什么
- 再决定为消除这个风险需要什么组件
- 没有风险 → 不增加组件

对应你 SOP-07「报价签约」"别按 Agent 数量报价"——
多一个 Agent 就多一份维护成本和故障面。

2. 风险驱动决策矩阵

风险 引入组件 你的 SOP 映射
AI 写错数据 Harness + 业务回滚 SOP-03 第 3 步（立刚性规则）
多模型切换混乱 模型网关 Middle 04-工具链.md
数据被滥用 权限 + 审计 + 数据隔离 B4 整本
知识过期 RAG 定期更新 B3 整本
Agent 死循环 超时 + 重试上限 B2 状态管理
误删数据 软删除 + 二次确认 A2 护栏
服务不可用 多活 + 降级 B1 灰度发布
内容违规 输入输出过滤 B4 内容安全

决策口诀：识别风险 → 选最简组件 → 验证风险消除 → 否则升级组件。

3. 三个"什么时候不上"的问题

这套方法论最有价值的部分。

问题 答案
什么时候不上 RAG？ 知识不更新 / 不需要可溯源
什么时候不上微服务？ 团队 < 5 人 / 业务没跑通
什么时候不上多 Agent？ 流程没标准化 / 业务没定型

对应你的「先 Demo 再谈全案」——
永远先做最简方案，跑通再升级。

4. 风险 = 损失 × 概率

不是所有风险都值得解决：

风险 损失 概率 优先级
误删核心数据 高 低 高（必须解决）
偶发幻觉回答 中 中 中（必须解决）
接口偶尔慢 低 中 低（可接受）
完全宕机 极高 极低 中（业务连续性方案）

优先级 = 损失 × 概率。低优先级风险不该消耗你的工程预算。

三、关键术语

英文 中文 释义
Risk-Driven 风险驱动 架构决策依据是风险

五、客户引用话术

"我们的架构不是堆出来的，是按风险驱动的——
每加一个组件都对应消除一个具体风险。
这套做法参照《Software Architecture》里的 Risk-Driven Architecture，
保证您花钱买的是问题解决方案，不是技术炫耀。"

十一、3 个组件决策矩阵

决策 1：要不要上 RAG？

条件 必须 RAG 不必 RAG
数据更新频率 > 每周 < 每月
数据来源 私有 / 敏感 公开
答案要求 可溯源 不需要
实时性 < 1 天 > 1 周

判断：4 个条件满足 2 个以上 = 用 RAG。

决策 2：要不要上多 Agent？

条件 多 Agent 单 Agent
任务复杂度 多步 / 多工具 单一任务
业务规模 > 10 业务流 < 3 业务流
团队规模 > 3 FDE 1 FDE
维护能力 有专人 1 人兼

判断：4 个条件满足 2 个以上 = 用多 Agent。

决策 3：要不要私有部署？

条件 私有部署 公网 API
数据敏感 高（金融/医疗） 低（一般业务）
合规要求 等保三级 无
流量规模 > 100K/天 < 10K/天
成本预算 > 100 万/年 < 10 万/年

判断：4 个条件满足 2 个以上 = 私有部署。

十二、常见反模式

反模式 1：为了"看起来专业"加组件

症状：Demo 阶段就上微服务 + K8s + 多 Agent。
风险：复杂度爆炸 + 维护成本高。
正解：先单 Agent 跑通，再升级。

反模式 2：组件越多越好

症状：每个技术都"先加上再说"。
风险：技术债 + 没人能维护。
正解：每个组件对应消除一个具体风险。

十一、原文核心（Risk-Driven Architecture 工业实践）

综合自 Microsoft Architecture Guides + NIST 风险框架 + ThoughtWorks 实践

1. 风险驱动架构的核心思想

"Architect for risk, not for features.
Every architectural component should exist because it mitigates a specific risk."

翻译：为风险做架构，不为功能做架构。
每个架构组件存在的原因 = 缓解某个具体风险。

2. 风险 = 损失 × 概率

不是所有风险都值得解决：
- 损失 × 概率 = 风险值
- 风险值高 = 必须解决
- 风险值低 = 可接受

风险 损失 概率 风险值 优先级
数据泄露 高 中 高 必须解决
AI 幻觉 中 高 高 必须解决
接口超时 低 中 低 可接受
误删数据 高 低 中 应解决

3. 组件引入决策矩阵

风险等级 引入组件 决策
没有风险 不加 YAGNI（不需要就别做）
有风险 / 低 简单措施 最小成本
有风险 / 中 标准组件 选成熟方案
有风险 / 高 复杂方案 多重防护

4. 5 个常见决策

决策 1：要不要上 RAG？

  • 数据更新 > 每周 + 需要可溯源 = 用 RAG
  • 数据稳定 + 创意任务 = 不用

决策 2：要不要上多 Agent？

  • 业务流 > 10 + 团队 > 3 FDE = 用多 Agent
  • 业务流 < 3 + 1 FDE = 单 Agent 足够

决策 3：要不要私有部署？

  • 数据敏感 + 合规要求 = 私有部署
  • 流量 < 10K/天 = 云 API

决策 4：要不要上中间网关？

  • 多模型 + 多业务 = 加中间网关
  • 单模型 + 单业务 = 直接调

决策 5：要不要 Rerank？

  • 召回 > 100 个 = 加 Rerank
  • 召回 < 10 个 = 不需要

5. 7 个反模式

  1. 为"看起来专业"加组件
  2. 组件越多越好
  3. 不识别风险就设计
  4. KPI 倒挂：KPI 倒过来驱动架构
  5. 不可逆决策：架构决策没留 rollback 余地
  6. 忽视合规：法务/合规早期不介入
  7. 过度设计：为不存在的需求设计
