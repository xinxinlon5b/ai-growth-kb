C1 · 风险驱动架构设计（Risk-Driven Architecture）

类型：通用软件架构方法论
来源：《Software Architecture: Foundations, Theory, and Practice》
中文卡版本：基于摘要整理 · 2026-09-10

一、定位

这是最反"AI 一上来就上架构"的方法论——
架构决策由风险驱动，不是由"听起来高级"驱动。

你的方法论「工具是 0，业务才是 1」就是这套思想的本地化表达。

二、核心论点

1. 架构组件不是越多越好

反模式（企业 AI 项目常见）：
- 上来就搭微服务
- 上来就接向量数据库
- 上来就上 K8s
- 上来就搞多模态
- 上来就搞 AutoML

正解：
- 先识别风险是什么
- 再决定为消除这个风险需要什么组件
- 没有风险 → 不增加组件

对应你 SOP-07「报价签约」"别按 Agent 数量报价"——
多一个 Agent 就多一份维护成本和故障面。

2. 风险驱动决策矩阵

风险 引入组件 你的 SOP 映射
AI 写错数据 Harness + 业务回滚 SOP-03 第 3 步（立刚性规则）
多模型切换混乱 模型网关 Middle 04-工具链.md
数据被滥用 权限 + 审计 + 数据隔离 B4 整本
知识过期 RAG 定期更新 B3 整本
Agent 死循环 超时 + 重试上限 B2 状态管理
误删数据 软删除 + 二次确认 A2 护栏
服务不可用 多活 + 降级 B1 灰度发布
内容违规 输入输出过滤 B4 内容安全

决策口诀：识别风险 → 选最简组件 → 验证风险消除 → 否则升级组件。

3. 三个"什么时候不上"的问题

这套方法论最有价值的部分。

问题 答案
什么时候不上 RAG？ 知识不更新 / 不需要可溯源
什么时候不上微服务？ 团队 < 5 人 / 业务没跑通
什么时候不上多 Agent？ 流程没标准化 / 业务没定型

对应你的「先 Demo 再谈全案」——
永远先做最简方案，跑通再升级。

4. 风险 = 损失 × 概率

不是所有风险都值得解决：

风险 损失 概率 优先级
误删核心数据 高 低 高（必须解决）
偶发幻觉回答 中 中 中（必须解决）
接口偶尔慢 低 中 低（可接受）
完全宕机 极高 极低 中（业务连续性方案）

优先级 = 损失 × 概率。低优先级风险不该消耗你的工程预算。

三、关键术语

英文 中文 释义
Risk-Driven 风险驱动 架构决策依据是风险
YAGNI You Aren't Gonna Need It 不需要就别做
KISS Keep It Simple, Stupid 越简单越好
Over-Engineering 过度工程 加了一堆没用的组件

五、客户引用话术

"我们的架构不是堆出来的，是按风险驱动的——
每加一个组件都对应消除一个具体风险。
这套做法参照《Software Architecture》里的 Risk-Driven Architecture，
保证您花钱买的是问题解决方案，不是技术炫耀。"
