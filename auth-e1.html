E1 · 软件工程知识体系（SWEBOK + ISO 12207 + Agile + Scrum + CMMI + DORA）

类型：通用软件工程方法论 · 权威标准
来源：DeerFlow 调研报告（2026-09-09），原文「软件是如何开发出来的」
中文卡版本：基于 DeerFlow 调研整理 · 2026-09-10
链接：https://xinxinlon5b.github.io/growth-panel-online/obs/成长系统/27_deerflow权威调研报告_软件工程与企业AI落地_v1.md

一、定位

这一张是整个软件工程的"总地图"——讲清楚「软件从 0 到 1 是怎么被开发出来的」。你的方法论和方法论簇里所有"做事的步骤"，都对应到这套骨架上。

FDE 写的不是"AI 代码"，是"企业级生产软件"——必须按这套工程标准做。
见客户时引用 SWEBOK / ISO 12207 / DORA，比"我做了 10 年"有说服力得多。

二、两大"总地图"

SWEBOK V4（软件工程知识体系）

IEEE 计算机学会发布的《软件工程知识体系指南 V4》，把软件工程知识划分为 18 个知识领域（KA）。

核心 18 个 KA：
- 软件需求 / 设计 / 构造 / 测试 / 维护
- 软件配置管理 / 工程管理 / 工程过程 / 工程模型与方法
- 软件质量 / 工程专业实践 / 工程经济学
- 计算基础 / 数学基础 / 工程基础
- 软件安全（新增）/ 软件操作（新增）

回答"做软件需要哪些知识/工种"——相当于知识地图。

ISO/IEC/IEEE 12207:2026（软件生命周期过程）

国际标准，把软件生命周期需要执行的过程划分为 4 大组：

过程组 做什么 例子
协议过程（Agreement） 客户/供应商契约 获取、供应
组织项目使能过程 组织级基础设施 资产管理、人才管理
技术管理过程 项目层管理 规划、评估、风险、决策、配置、质量
技术过程 真正造软件 需求、设计、实现、集成、验证、转移、操作、维护、报废

回答"做软件要按什么顺序做什么"——相当于动作地图。
SWEBOK + 12207 = 知识全集 + 动作全集 = 软件工程最权威答案

三、生命周期模型（SDLC）

模型 核心思想 适用场景 出处
瀑布 需求→设计→实现→测试→部署 严格线性 需求稳定、风险低（航天/军工） Winston Royce, 1970
V 模型 瀑布 + 每阶段对应验证环节 质量要求高、可追溯 ISO 12207
迭代/增量 分多次循环，每次一个可用增量 需求演进的中大型 —
螺旋 每个循环做风险评估 高风险、创新 Barry Boehm, 1988
敏捷（Agile） 小步快跑、频繁交付、拥抱变化 互联网/产品类 2001 敏捷宣言

敏捷宣言 4 价值观 + 12 原则（2001）

4 价值观：
1. 个体与互动 > 流程与工具
2. 可工作的软件 > 详尽的文档
3. 客户协作 > 合同谈判
4. 响应变化 > 遵循计划

12 原则（节选）：尽早持续交付 / 欢迎需求变化 / 频繁交付 / 业务人员与开发者每天一起工作 / 以可工作的软件为进度度量 / 追求技术卓越 / 简洁 / 团队定期反思调整。

为什么敏捷成为主流：缩短反馈环，把"猜错需求"的成本降到最低。
https://agilemanifesto.org/

四、Scrum 框架

Scrum Guide 定义了 Scrum 的标准结构：

类别 内容
3 角色 产品负责人（PO）/ Scrum Master / 开发团队
5 事件 Sprint / Sprint 计划会 / 每日站会 / Sprint 评审会 / Sprint 回顾会
3 工件 产品待办列表 / Sprint 待办列表 / 增量

https://scrumguides.org/

五、CMMI 5 级成熟度

组织过程能力的 5 个等级：
1. 初始级——靠个人英雄
2. 已管理级——项目可重复
3. 已定义级——组织级标准化
4. 定量管理级——数据驱动
5. 优化级——持续改进

https://cmmiinstitute.com/

六、DORA 4 项关键指标（DevOps 度量）

衡量软件交付能力的行业标准：

指标 衡量什么 优秀值
部署频率 多频繁发布到生产 随时
变更前置时间 提交代码到上线耗时 < 1 天
变更失败率 上线导致故障比例 < 15%
恢复时间（MTTR） 故障后多久恢复 < 1 小时

DORA 是 FDE 报价时自证能力的最强武器——告诉客户"我的 DORA 四项是 X / Y / Z / W"。
https://cloud.google.com/blog/products/devops-sre/using-the-four-keys-to-measure-your-devops-performance

七、23 种设计模式（GoF）

经典著作《Design Patterns》总结的 23 种 模式分三大类：
- 创建型（5）——对象如何创建：单例、工厂、建造者...
- 结构型（7）——对象如何组合：适配器、装饰器、代理...
- 行为型（11）——对象如何协作：观察者、策略、命令...

Agent 工作流编排本质就是行为型模式的应用。

十一、DORA 4 指标自测模板

自测问题（每月填一次）

1. 部署频率
   - 上个月部署到生产几次？___ 次
   - 平均多久部署一次？___ 天
   - 评分：☐ Elite（按需） ☐ High（每周-每天） ☐ Medium（每月-每周） ☐ Low（> 每月）

2. 变更前置时间
   - 从代码提交到生产部署平均多久？___ 小时
   - 评分：☐ Elite（< 1 天） ☐ High（1 天-1 周） ☐ Medium（1 周-1 月） ☐ Low（> 1 月）

3. 变更失败率
   - 上个月导致故障 / 回滚的部署比例？___ %
   - 评分：☐ Elite（0-15%） ☐ High（16-30%） ☐ Medium（31-45%） ☐ Low（> 46%）

4. 恢复时间（MTTR）
   - 上个月生产故障平均恢复时间？___ 小时
   - 评分：☐ Elite（< 1 小时） ☐ High（< 1 天） ☐ Medium（< 1 周） ☐ Low（> 1 周）

改进方向

弱项 改进措施
部署频率低 CI/CD 自动化 + 减少审批
前置时间长 拆分大变更 + 并行测试
失败率高 自动化测试 + 灰度发布
MTTR 长 监控告警 + 回滚预案

十二、3 个反模式

反模式 1：把 DORA 当 KPI 考核

症状：用 DORA 排名 / 扣奖金。
风险：团队为指标做指标（伪造部署 / 瞒报故障）。
正解：DORA 是改进工具，不是考核工具。

反模式 2：只追一项

症状：只优化部署频率（导致失败率上升）。
风险：速度换质量。
正解：4 项平衡看。

反模式 3：不测就改

症状：直接上 CI/CD 不测基线。
风险：改完不知道变好还是变差。
正解：先测 3 个月基线，再定改进目标。
